## 1. 예약 생성 (리스크 점수: 9점)

**핵심 인수 조건**: "고객이 유효한 정보로 예약 가능한 사이트와 날짜를 선택하면 예약이 확정되고, 확인 코드가 발급된다."

---

### 1.1 정상 예약 생성

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 캠핑장을 이용하려는 신규 고객 |
| **What** | 원하는 캠핑 사이트에 예약을 생성한다 |
| **When** | 예약 가능한 날짜(오늘 이후 ~ 30일 이내)에 빈 사이트가 있을 때 |
| **Where** | 예약 시스템 (`POST /api/reservations`) |
| **Why** | 고객은 캠핑 사이트 이용권을 확보하고, 캠핑장은 매출을 확정한다 |
| **How** | 고객 정보(이름, 전화번호), 사이트 번호, 예약 기간을 입력하여 요청한다 |

#### 시나리오

```gherkin
Given: A-1 사이트가 2026년 2월 1일부터 2월 3일까지 예약 가능한 상태이다.
When: 홍길동이 A-1 사이트를 2026년 2월 1일부터 2월 3일까지 예약한다.
Then: 예약이 성공적으로 생성된다.
And: 6자리 확인 코드가 발급된다.
And: 예약 상태가 "CONFIRMED"로 설정된다.
```

#### 검증 포인트

- [ ] 예약 성공 시 201 Created 응답
- [ ] 확인 코드 6자리 (영문대문자 + 숫자) 발급
- [ ] 예약 정보(고객명, 날짜, 사이트) 정확히 저장

---

### 1.2 중복 예약 방지

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 이미 예약된 사이트를 예약하려는 고객 |
| **What** | 다른 고객이 예약한 사이트/날짜에 중복 예약을 시도한다 |
| **When** | 해당 사이트가 특정 기간에 이미 예약되어 있을 때 |
| **Where** | 예약 시스템 (`POST /api/reservations`) |
| **Why** | 하나의 사이트는 같은 날짜에 한 고객만 이용할 수 있어야 한다 (데이터 무결성) |
| **How** | 시스템이 예약 충돌을 감지하고 요청을 거부한다 |

#### 시나리오

```gherkin
Given: A-1 사이트가 2026년 2월 1일부터 2월 3일까지 홍길동에게 예약되어 있다.
When: 김철수가 A-1 사이트를 2026년 2월 2일부터 2월 4일까지 예약 시도한다.
Then: 예약이 거부된다.
And: "해당 기간에 이미 예약이 존재합니다." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 중복 기간 예약 시 409 Conflict 응답
- [ ] 기존 예약과 1일이라도 겹치면 거부
- [ ] 에러 메시지에 충돌 사유 명시

---

### 1.3 과거 날짜 예약 불가

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 과거 날짜로 예약하려는 고객 |
| **What** | 이미 지나간 날짜에 예약을 시도한다 |
| **When** | 시작일이 오늘보다 이전일 때 |
| **Where** | 예약 시스템 (`POST /api/reservations`) |
| **Why** | 과거에는 캠핑장을 이용할 수 없으므로 논리적으로 불가능한 예약을 방지한다 |
| **How** | 시스템이 시작일과 오늘 날짜를 비교하여 거부한다 |

#### 시나리오

```gherkin
Given: 오늘 날짜가 2026년 1월 13일이다.
When: 홍길동이 A-1 사이트를 2026년 1월 10일부터 1월 12일까지 예약 시도한다.
Then: 예약이 거부된다.
And: "과거 날짜로 예약할 수 없습니다." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 시작일이 오늘보다 이전이면 거부
- [ ] 오늘 날짜 예약은 허용
- [ ] 409 Conflict 응답

---

### 1.4 예약 기간 제한 (최대 30일)

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 장기 예약을 원하는 고객 |
| **What** | 30일을 초과하는 기간으로 예약을 시도한다 |
| **When** | 예약 기간이 30일을 초과할 때 |
| **Where** | 예약 시스템 (`POST /api/reservations`) |
| **Why** | 장기 독점을 방지하고 다른 고객에게 공평한 기회를 제공한다 |
| **How** | 시스템이 시작일과 종료일의 차이를 계산하여 거부한다 |

#### 시나리오

```gherkin
Given: A-1 사이트가 예약 가능한 상태이다.
When: 홍길동이 A-1 사이트를 2026년 2월 1일부터 3월 15일까지 (42일) 예약 시도한다.
Then: 예약이 거부된다.
And: "예약 기간은 최대 30일입니다." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 30일 초과 예약 시 거부
- [ ] 정확히 30일 예약은 허용
- [ ] 409 Conflict 응답

### 1.5 필수 정보 누락 - 예약자 이름

#### 5W1H 분석

|------|------|
| **Who** | 필수 정보를 누락한 고객 |

| **When** | 예약 폼에서 이름 필드가 비어있을 때 |
| **Where** | 예약 시스템 (`POST /api/reservations`) |
| **Why** | 예약자 식별 및 현장 확인을 위해 이름은 필수이다 |
| **How** | 시스템이 필수 필드 검증 후 거부한다 |

#### 시나리오

```gherkin
Given: 고객이 예약 폼을 작성 중이다.
When: 예약자 이름 없이 예약을 시도한다.
Then: 예약이 거부된다.
And: "예약자 이름을 입력해주세요." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 이름 미입력 시 거부
- [ ] 이름 2자 미만 시 거부
- [ ] 이름 20자 초과 시 거부
- [ ] 409 Conflict 응답

### 1.6 필수 정보 누락 - 전화번호 형식

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 잘못된 전화번호를 입력한 고객 |
| **What** | 올바르지 않은 형식의 전화번호로 예약을 시도한다 |
| **When** | 전화번호가 10~11자리 숫자가 아닐 때 |
| **Where** | 예약 시스템 (`POST /api/reservations`) |
| **Why** | 예약 확인 및 긴급 연락을 위해 유효한 전화번호가 필요하다 |
| **How** | 시스템이 전화번호 형식을 검증하여 거부한다 |

#### 시나리오

```gherkin
Given: 고객이 예약 폼을 작성 중이다.
When: 전화번호 "123"으로 예약을 시도한다.
Then: 예약이 거부된다.
And: "전화번호 형식이 올바르지 않습니다." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 10자리 미만 시 거부
- [ ] 12자리 이상 시 거부
- [ ] 숫자 외 문자 포함 시 거부
- [ ] 하이픈 포함 형식(010-1234-5678)은 허용

### 1.7 동시 예약 요청 처리

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 같은 사이트를 동시에 예약하려는 여러 고객 |
| **What** | 동일한 사이트/날짜에 동시에 예약 요청을 보낸다 |
| **When** | 두 요청이 거의 동시에 서버에 도착할 때 |
| **Where** | 예약 시스템 (`POST /api/reservations`) |
| **Why** | 데이터 정합성을 유지하고 이중 예약을 방지한다 (Race Condition 방지) |
| **How** | 시스템이 동시성 제어를 통해 한 건만 성공시킨다 |

#### 시나리오

```gherkin
Given: A-1 사이트가 2026년 2월 1일에 예약 가능한 상태이다.
When: 홍길동과 김철수가 동시에 같은 날짜로 A-1 사이트 예약을 요청한다.
Then: 한 명의 예약만 성공한다.
And: 나머지 한 명은 "해당 기간에 이미 예약이 존재합니다." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 동시 요청 시 한 건만 성공
- [ ] 중복 예약 데이터 생성 방지
- [ ] 실패한 요청에 명확한 에러 메시지

## 2. 예약 수정 (리스크 점수: 8점)

**핵심 인수 조건**: "고객이 올바른 확인 코드를 입력하고, 변경하려는 날짜와 사이트가 예약 가능하면 예약 정보가 수정된다."

---

### 2.1 정상 예약 수정

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 기존 예약을 변경하려는 고객 |
| **What** | 예약 날짜를 다른 날짜로 변경한다 |
| **When** | 변경하려는 날짜가 예약 가능할 때 |
| **Where** | 예약 시스템 (`PUT /api/reservations/{id}`) |
| **Why** | 고객의 일정 변경에 유연하게 대응하여 취소를 방지한다 |
| **How** | 확인 코드로 본인 인증 후, 변경할 정보를 입력한다 |

#### 시나리오

```gherkin
Given: 홍길동이 A-1 사이트를 2026년 2월 1일~3일로 예약했고, 확인 코드는 "ABC123"이다.
When: 홍길동이 확인 코드 "ABC123"을 입력하고 날짜를 2월 5일~7일로 변경한다.
Then: 예약 날짜가 2월 5일~7일로 수정된다.
And: 기존 확인 코드 "ABC123"은 유지된다.
```

#### 검증 포인트

- [ ] 수정 성공 시 200 OK 응답
- [ ] 변경된 정보 정확히 반영
- [ ] 확인 코드는 변경되지 않음

---

### 2.2 잘못된 확인 코드로 수정 시도

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 잘못된 확인 코드를 입력한 고객 (또는 악의적 사용자) |
| **What** | 틀린 확인 코드로 타인의 예약을 수정하려 시도한다 |
| **When** | 입력한 확인 코드가 실제 예약의 확인 코드와 다를 때 |
| **Where** | 예약 시스템 (`PUT /api/reservations/{id}`) |
| **Why** | 본인 확인을 통해 무단 예약 변경을 방지한다 (보안) |
| **How** | 시스템이 확인 코드를 검증하여 불일치 시 거부한다 |

#### 시나리오

```gherkin
Given: 홍길동의 예약 확인 코드는 "ABC123"이다.
When: 확인 코드 "WRONG1"을 입력하고 예약 수정을 시도한다.
Then: 수정이 거부된다.
And: "확인 코드가 일치하지 않습니다." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 잘못된 확인 코드 시 400 Bad Request 응답
- [ ] 예약 정보 변경 없음
- [ ] 보안 로그 기록 권장

---

### 2.3 다른 예약과 충돌하는 날짜로 수정

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 예약 날짜를 변경하려는 고객 |
| **What** | 다른 고객이 이미 예약한 날짜로 변경을 시도한다 |
| **When** | 변경하려는 날짜에 동일 사이트의 다른 예약이 있을 때 |
| **Where** | 예약 시스템 (`PUT /api/reservations/{id}`) |
| **Why** | 예약 충돌을 방지하고 기존 예약자의 권리를 보호한다 |
| **How** | 시스템이 자기 예약을 제외한 충돌 검사를 수행한다 |

#### 시나리오

```gherkin
Given: 홍길동이 A-1 사이트를 2월 1일~3일로 예약했다.
And: 김철수가 A-1 사이트를 2월 5일~7일로 예약했다.
When: 홍길동이 자신의 예약을 2월 5일~7일로 변경 시도한다.
Then: 수정이 거부된다.
And: "해당 기간에 이미 예약이 존재합니다." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 다른 예약과 충돌 시 거부
- [ ] 자기 자신의 기존 예약은 충돌 검사에서 제외
- [ ] 409 Conflict 응답

---

### 2.4 사이트 변경

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 다른 사이트로 변경하려는 고객 |
| **What** | 예약한 사이트를 다른 사이트로 변경한다 |
| **When** | 새 사이트가 해당 기간에 예약 가능할 때 |
| **Where** | 예약 시스템 (`PUT /api/reservations/{id}`) |
| **Why** | 고객이 더 적합한 사이트를 선택할 수 있게 한다 |
| **How** | 확인 코드 인증 후 새 사이트 번호를 입력한다 |

#### 시나리오

```gherkin
Given: 홍길동이 A-1 사이트를 2월 1일~3일로 예약했다.
And: B-1 사이트가 같은 기간에 예약 가능하다.
When: 홍길동이 사이트를 B-1로 변경한다.
Then: 예약 사이트가 B-1로 수정된다.
And: A-1 사이트는 해당 기간 예약 가능 상태가 된다.
```

#### 검증 포인트

- [ ] 사이트 변경 시 새 사이트 예약 가능 여부 확인
- [ ] 기존 사이트 가용성 복구
- [ ] 200 OK 응답

---

### 2.5 확인 코드 미입력

#### 5W1H 분석

|------|------|

| **When** | 수정 요청에 확인 코드 파라미터가 없을 때 |

#### 시나리오

```gherkin
Given: 홍길동이 예약을 보유하고 있다.
When: 확인 코드 없이 예약 수정을 시도한다.
Then: 수정이 거부된다.
And: "확인 코드를 입력해주세요." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 확인 코드 미입력 시 거부
- [ ] 400 Bad Request 응답
- [ ] 보안을 위한 필수 인증

## 3. 예약 취소 (리스크 점수: 7점)

**핵심 인수 조건**: "고객이 올바른 확인 코드를 입력하면 예약이 취소되고, 해당 사이트는 즉시 예약 가능 상태가 된다."

---

### 3.1 정상 예약 취소 (사전 취소)

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 예약을 취소하려는 고객 |
| **What** | 예약 시작일 이전에 예약을 취소한다 |
| **When** | 오늘이 예약 시작일보다 이전일 때 |
| **Where** | 예약 시스템 (`DELETE /api/reservations/{id}`) |
| **Why** | 고객의 일정 변경에 대응하고, 사이트를 다른 고객에게 제공한다 |
| **How** | 확인 코드로 본인 인증 후 취소를 요청한다 |

#### 시나리오

```gherkin
Given: 홍길동이 A-1 사이트를 2026년 2월 5일~7일로 예약했다.
And: 오늘 날짜는 2026년 2월 1일이다.
When: 홍길동이 올바른 확인 코드로 예약 취소를 요청한다.
Then: 예약이 취소된다.
And: 예약 상태가 "CANCELLED"로 변경된다.
And: A-1 사이트가 2월 5일~7일에 예약 가능해진다.
```

#### 검증 포인트

- [ ] 취소 성공 시 200 OK 응답
- [ ] 상태가 "CANCELLED"로 변경
- [ ] 해당 사이트/날짜 예약 가능 상태 복구

### 3.2 당일 취소

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 예약 당일에 취소하려는 고객 |
| **What** | 예약 시작일 당일에 예약을 취소한다 |
| **When** | 오늘이 예약 시작일과 같을 때 |
| **Where** | 예약 시스템 (`DELETE /api/reservations/{id}`) |
| **Why** | 당일 취소는 캠핑장 운영에 영향을 주므로 별도 상태로 관리한다 (향후 페널티/통계 활용) |
| **How** | 시스템이 취소 시점과 예약 시작일을 비교하여 상태를 결정한다 |

#### 시나리오

```gherkin
Given: 홍길동이 A-1 사이트를 2026년 2월 1일~3일로 예약했다.

```

- [ ] 예약 시작일 당일 취소 시 "CANCELLED_SAME_DAY" 상태
- [ ] 사전 취소와 당일 취소 구분
- [ ] 향후 정산/페널티 적용 가능한 데이터 유지

### 3.3 잘못된 확인 코드로 취소 시도

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 잘못된 확인 코드를 입력한 고객 (또는 악의적 사용자) |
| **What** | 틀린 확인 코드로 예약 취소를 시도한다 |
| **When** | 입력한 확인 코드가 실제 예약의 확인 코드와 다를 때 |
| **Where** | 예약 시스템 (`DELETE /api/reservations/{id}`) |
| **Why** | 본인 확인을 통해 무단 예약 취소를 방지한다 (보안) |
| **How** | 시스템이 확인 코드를 검증하여 불일치 시 거부한다 |

#### 시나리오

```gherkin
Given: 홍길동의 예약 확인 코드는 "ABC123"이다.
When: 확인 코드 "WRONG1"을 입력하고 예약 취소를 시도한다.
Then: 취소가 거부된다.
And: "확인 코드가 일치하지 않습니다." 메시지를 받는다.
```

#### 검증 포인트

- [ ] 잘못된 확인 코드 시 400 Bad Request 응답
- [ ] 예약 상태 변경 없음
- [ ] 보안 로그 기록 권장

### 3.5 취소 후 재예약 가능

#### 5W1H 분석

| 항목 | 내용 |
|------|------|
| **Who** | 취소된 사이트를 예약하려는 새로운 고객 |
| **What** | 다른 고객이 취소한 사이트/날짜를 예약한다 |
| **When** | 기존 예약이 취소된 직후 |
| **Where** | 예약 시스템 (`POST /api/reservations`) |
| **Why** | 취소된 사이트는 즉시 다른 고객에게 제공되어야 매출 손실을 최소화한다 |
| **How** | 취소 처리 시 사이트 가용성이 즉시 복구된다 |

#### 시나리오

```gherkin
Given: 홍길동이 A-1 사이트를 2월 5일~7일 예약 후 취소했다.
When: 김철수가 A-1 사이트를 2월 5일~7일로 예약한다.
Then: 예약이 성공한다.
And: 김철수에게 새로운 확인 코드가 발급된다.
```

#### 검증 포인트

- [ ] 취소된 예약의 사이트/날짜는 즉시 예약 가능
- [ ] 다른 고객이 해당 기간 예약 가능
- [ ] 새 예약에 새로운 확인 코드 발급
