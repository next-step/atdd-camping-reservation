# Top 3 인수 조건 (Acceptance Criteria)

## 공통 규칙
- 인수 조건은 “검증 가능한 한 문장”이어야 한다. (모호한 표현 금지)
- 검증 포인트는 체크리스트 형태로 작성한다.
- system-analysis에 있는 “전역 규칙/제약”과 충돌하지 않게 작성한다.

## 1) POST /api/reservations (예약 생성)
### 1-1. 5W1H 분석
| 항목 | 내용 |
|---|---|
| Who | 캠핑장 이용을 원하는 고객 |
| Why | 캠핑장 사이트와 기간을 예약하고 확정하기 위해 |
| When | 고객이 캠핑장 사이트와 예약 기간을 선택 후 예약 요청 시 |
| Where | `/api/reservations` (POST) |
| What | 새로운 캠핑장 예약 생성 |
| How | `ReservationRequest` (사이트 번호, 시작/종료일, 고객 이름, 전화번호)를 전송하고, 시스템은 유효성 검증, 중복 확인, 가격/포인트 계산 후 예약을 생성합니다. |

### 1-2. 인수 조건(한 문장)
고객은 유효한 정보로 예약 가능한 캠핑장 사이트를 선택하여 중복되지 않는 예약 기간에 새로운 캠핑장 예약을 성공적으로 생성하고 고유한 확인 코드를 발급받아야 합니다.

### 1-3. 검증 포인트(Checklist)
-   [ ] 유효한 `ReservationRequest`로 예약 생성 요청 시, HTTP 201 응답과 예약 정보(`id`, `confirmationCode` 등)를 반환하는가?
-   [ ] 예약 기간이 30일을 초과하는 경우, 예약 생성 요청 시 HTTP 400 응답과 에러 메시지를 반환하는가?
-   [ ] 예약 시작일이 과거인 경우, 예약 생성 요청 시 HTTP 400 응답과 에러 메시지를 반환하는가?
-   [ ] 종료일이 시작일보다 이전인 경우, 예약 생성 요청 시 HTTP 400 응답과 에러 메시지를 반환하는가?
-   [ ] 존재하지 않는 사이트 번호로 예약 생성 요청 시, HTTP 400 응답과 에러 메시지를 반환하는가?
-   [ ] 이름이 2자 미만이거나 20자를 초과하는 경우, 예약 생성 요청 시 HTTP 400 응답과 에러 메시지를 반환하는가?
-   [ ] 전화번호 형식이 유효하지 않은 경우, 예약 생성 요청 시 HTTP 400 응답과 에러 메시지를 반환하는가?
-   [ ] 이미 예약된 캠핑장 사이트-기간에 대해 예약 생성 요청 시, HTTP 409 응답과 에러 메시지를 반환하는가?
-   [ ] 예약 생성 성공 시, 시스템에서 계산된 정확한 가격과 포인트가 반영되는가?
-   [ ] 예약 생성 시 고유한 6자리 `confirmationCode`가 발급되는가?
-   [ ] (동시성) 동일한 캠핑장-기간에 대해 여러 예약 요청이 동시에 발생할 경우, 하나의 요청만 성공하고 나머지 요청은 중복 에러(`HTTP 409`)를 반환하는가? (오버부킹 방지)

### 1-4. 경계/예외 케이스(키워드)
| 유형 | 케이스 |
|---|---|
| Validation | 필수 입력값 누락, 날짜 범위 초과, 이름/전화번호 형식 오류, 존재하지 않는 사이트 번호 |
| Authorization/Verification | N/A (인증 없음) |
| Concurrency/Consistency | 동일 사이트/기간 동시 예약 요청, 예약 생성 중 시스템 오류 시 데이터 롤백 |
| Data/State | 예약 생성 후 캠핑장 가용성 업데이트, 가격/포인트 계산 오류 |

## 2) DELETE /api/reservations/{id} (예약 취소)
### 2-1. 5W1H 분석
| 항목 | 내용 |
|---|---|
| Who | 예약을 취소하려는 고객 |
| Why | 예약된 캠핑장 이용을 원하지 않아 예약을 취소하기 위해 |
| When | 고객이 예약 ID와 확인 코드를 입력하여 취소 요청 시 |
| Where | `/api/reservations/{id}` (DELETE) |
| What | 기존 캠핑장 예약 취소 |
| How | 예약 ID와 `confirmationCode`를 전송하여 해당 예약을 취소 상태로 변경합니다. |

### 2-2. 인수 조건(한 문장)
고객은 자신의 예약 ID와 정확한 확인 코드를 제공하여 예약을 성공적으로 취소할 수 있어야 하며, 시스템은 예약 상태를 `CANCELLED`로 변경하고, 당일 취소 시 `CANCELLED_SAME_DAY` 상태를 정확히 반영해야 합니다.

### 2-3. 검증 포인트(Checklist)
-   [ ] 유효한 예약 ID와 정확한 `confirmationCode`로 취소 요청 시, HTTP 200 응답과 성공 메시지를 반환하는가?
-   [ ] 예약 취소 성공 후, 해당 예약의 상태가 `CANCELLED`로 변경되었는지 확인하는가?
-   [ ] 예약 시작일과 동일한 날짜에 취소 요청 시, 예약 상태가 `CANCELLED_SAME_DAY`로 변경되는가?
-   [ ] 존재하지 않는 예약 ID로 취소 요청 시, HTTP 404 응답과 에러 메시지를 반환하는가?
-   [ ] 유효하지 않거나 일치하지 않는 `confirmationCode`로 취소 요청 시, HTTP 400 응답과 에러 메시지를 반환하는가?
-   [ ] 이미 취소된 예약을 다시 취소 요청 시, 시스템은 적절한 에러(`HTTP 400`)를 반환하는가?
-   [ ] (보안) 타인의 `id`와 임의의 `confirmationCode`로 취소 요청 시, 실패(`HTTP 400`)하는가?

### 2-4. 경계/예외 케이스(키워드)
| 유형 | 케이스 |
|---|---|
| Validation | 존재하지 않는 예약 ID, 유효하지 않은/일치하지 않는 `confirmationCode` |
| Authorization/Verification | `confirmationCode`의 무단 사용 시도 |
| Concurrency/Consistency | 동시에 여러 취소 요청, 취소와 동시에 예약 업데이트 시도 |
| Data/State | 이미 취소된 예약 재취소 시도, 예약 당일 취소 |

## 3) GET /api/reservations/my (내 예약 목록 조회)
### 3-1. 5W1H 분석
| 항목 | 내용 |
|---|---|
| Who | 자신의 예약을 확인하려는 고객 |
| Why | 본인이 예약한 캠핑장 예약 내역을 편리하게 확인하기 위해 |
| When | 고객이 이름과 전화번호를 입력하여 예약 내역 조회를 요청 시 |
| Where | `/api/reservations/my` (GET) |
| What | 고객의 이름과 전화번호에 해당하는 예약 목록 조회 |
| How | `name`과 `phone` 쿼리 파라미터를 전송하여 해당 정보를 조회합니다. |

### 3-2. 인수 조건(한 문장)
고객은 자신의 이름과 전화번호를 정확히 제공하여 본인의 예약 목록을 조회할 수 있어야 하지만, 타인의 정보를 이용한 무단 조회 시도에는 시스템이 예약 목록을 반환하지 않아야 합니다.

### 3-3. 검증 포인트(Checklist)
-   [ ] 유효한 고객 이름과 전화번호로 요청 시, 해당 고객의 예약 목록(`List<ReservationResponse>`)을 HTTP 200 응답으로 반환하는가?
-   [ ] 조회된 예약 목록에 `ReservationRepository.findByCustomerNameAndPhoneNumber`로 검색된 예약만 포함되는가?
-   [ ] 존재하지 않는 고객 이름/전화번호 조합으로 요청 시, 빈 목록(`[]`) 또는 HTTP 404 (필요시) 응답을 반환하는가? (현재는 빈 목록 반환)
-   [ ] (보안) 타인의 이름과 전화번호를 임의로 조합하여 요청 시, 해당 타인의 예약 목록이 노출되지 않고 빈 목록(`[]`)을 반환하는가?
-   [ ] 이름 또는 전화번호 중 하나라도 누락된 경우, HTTP 400 응답과 에러 메시지를 반환하는가?
-   [ ] 전화번호 형식이 유효하지 않은 경우, HTTP 400 응답과 에러 메시지를 반환하는가?

### 3-4. 경계/예외 케이스(키워드)
| 유형 | 케이스 |
|---|---|
| Validation | 이름/전화번호 누락, 전화번호 형식 오류 |
| Authorization/Verification | 타인의 이름/전화번호를 이용한 무단 조회 시도 |
| Concurrency/Consistency | N/A (단순 조회) |
| Data/State | 이름/전화번호가 일치하는 예약이 없는 경우 |
