# T-1 인수 조건

고객센터 신고: "오늘로부터 30일 넘게 남은 날짜인데 예약이 됩니다."

```
규칙   예약 시작일은 오늘로부터 30일 이내여야 한다
이유   한 달 너머는 운영 일정이 확정되지 않아 받지 않는다.

Given  기준일 2026-08-16, 시드가 쓰지 않는 사이트
When   POST 시작일 = 오늘+30일 (09-15)              Then  201 Created, confirmationCode 발급 (실측 T7MG9X)
When   POST 시작일 = 오늘+31일 (09-16)              Then  (버그) 201 성공 → 기대 409 "오늘로부터 30일 이내 날짜만 예약 가능합니다."
When   POST 시작일 = 오늘+60일 (10-15)              Then  (버그) 201 성공 → 기대 409
When   PUT  기존 예약 시작일만 +31일 수정 (종료일 생략)     Then  (버그) 200 성공 → 기대 400 (수정 실패 컨벤션)
When   PUT  기존 예약 시작일+종료일 모두 +31일 수정          Then  (버그) 200 성공 → 기대 400

질문   체류 기간(체크인~체크아웃) 30일 초과 제한도 PUT 경로에 적용해야 하는가
       → createReservation에는 있으나 updateReservation에는 없다(수정 경로에서
       30일 초과 체류 기간으로 변경해도 허용됨). "오늘로부터 30일 이내"인 이
       규칙과는 별개의 체크다. T-4로 분리, 이 티켓에서는 판단하지 않는다.
```

```
규칙   과거 날짜로 예약할 수 없고, 종료일이 시작일보다 이전일 수 없다
이유   날짜가 역전된 예약이 저장되면 가격·포인트 계산 루프가 0회 실행돼
       0원으로 처리된다.

Given  기준일 2026-08-17
When   POST 시작일 = 과거 (08-16)                  Then  409 "과거 날짜로 예약할 수 없습니다." (정상)
When   POST 종료일 < 시작일 (08-18~08-17)            Then  409 "종료일이 시작일보다 이전일 수 없습니다." (정상)
When   PUT  기존 예약 시작일+종료일 모두 과거로 수정          Then  400 "과거 날짜로 예약할 수 없습니다." (정상)
When   PUT  기존 예약 시작일만 과거로 수정 (종료일 생략)       Then  (버그) 200 성공 → 기대 400
```

```
규칙   예약 완료 시 6자리 영숫자 확인 코드([A-Z0-9]{6})가 생성된다
이유   확인 코드는 예약 수정·취소 시 본인 확인 수단이다. 코드 없이 예약이
       생성되면 이후 수정·취소 API를 호출할 수 없다. 현재 정상 동작이지만
       회귀 방지를 위해 인수 조건으로 명시한다.

Given  기준일 2026-08-17, 시드가 쓰지 않는 사이트
When   POST 정상 요청                              Then  201, confirmationCode가 [A-Z0-9]{6} 형식
                                                    (실측 5회: A7FF89, OPK9HM, I0CF3R, UY5ORJ, 6W4PPM)

질문   실제 생성 로직과 별도로 존재하는 generateConfirmationCode() 데드코드를
       실사용 로직으로 교체할지, 제거할지 → 동일한 코드 생성 로직이 예약 생성
       경로에 인라인으로 중복 구현돼 있고, 이 메서드는 어디서도 호출되지 않는다.
       T-5로 분리, 이 티켓에서는 판단하지 않는다.
```

# T-2 인수 조건

고객센터 신고: "전화번호를 안 넣었는데 예약이 완료됐습니다."

```
규칙   전화번호는 필수다 — 없거나(필드 누락/null) 빈 문자열이거나 공백만이면
       예약할 수 없다. PUT에서 필드를 아예 보내지 않으면(다른 필드만 수정)
       기존 값을 그대로 둔다 — "건드리지 않음"과 "빈 값으로 지움"은 다른 요청이다.
이유   전화번호는 예약 확인 알림(SMS 시뮬레이션)과 이름+전화번호 조회의
       유일한 키다.

Given  기준일 2026-08-17, 시드가 쓰지 않는 사이트
When   POST phoneNumber 필드 없음                   Then  (버그) 201 성공 → 기대 409
When   POST phoneNumber = ""                       Then  (버그) 201 성공 → 기대 409
When   POST phoneNumber = "   "                     Then  (버그) 201 성공 → 기대 409
When   POST phoneNumber = "010-1111-2222" (정상)     Then  201 (정상, 회귀 방지)
When   POST phoneNumber = "123" (형식 오류)           Then  409 "전화번호 형식이 올바르지 않습니다." (정상 —
                                                    필수 검증이 이 형식 검증보다 먼저 실행되어야 한다)
When   PUT  기존 예약 phoneNumber = ""                Then  (버그) 200 성공 → 기대 400 (수정 실패 컨벤션)
When   PUT  기존 예약 phoneNumber = "   "              Then  (버그) 200 성공 → 기대 400
When   PUT  phoneNumber 필드 생략, 다른 필드만 수정        Then  200, 기존 phoneNumber 유지 (정상, 회귀 방지)
When   PUT  phoneNumber를 정상 형식의 새 값으로 수정        Then  200, 갱신됨 (정상, 회귀 방지)

질문   전화번호가 유일(unique)해야 하는가 → phoneNumber 컬럼에 unique 제약이
       없고, 동일한 전화번호로 몇 건이든 예약을 만들 수 있다. T-6으로 분리,
       이 티켓에서는 판단하지 않는다.

질문   전화번호 형식 규칙(현재 코드: '-' 제거 후 10~11자리 숫자만)을 정식
       인수 조건으로 명시해야 하는가, PUT에도 동일하게 적용해야 하는가 →
       updateReservation에는 형식 검증 자체가 없어 "abc" 같은 값도 그대로
       저장된다(실측 확인). T-7로 분리, 이 티켓에서는 판단하지 않는다.
```

# T-3 인수 조건

고객센터 신고: "예약을 취소했는데 같은 날짜에 다시 예약하려니 이미 예약이 있다고 나옵니다."

```
규칙   동일 사이트·동일 기간에 유효한(취소되지 않은) 예약이 이미 있으면
       생성(POST) 시 거부한다. 하루라도 겹치면 거부.
이유   같은 사이트·같은 기간에 두 예약이 겹치면 실제 이용 시 자리 충돌이 난다.
       신고 전제("같은 자리에 다시 예약하려니 이미 예약이 있다고 나온다")는
       생성(POST) 경로에서 벌어지는 일이라 이 규칙은 POST에 한정한다.

Given  기준일 2026-08-17, A-10에 기존 예약 2026-08-20~08-22 (CONFIRMED)
When   POST 완전 동일 기간 (08-20~08-22)              Then  409 "해당 기간에 이미 예약이 존재합니다." (정상)
When   POST 하루만 겹침 (08-22~08-24)                Then  409 (정상 — 시작일이 기존 종료일과 겹치면 거부)
When   POST 하루도 안 겹침 (08-23~08-24)              Then  201 (정상 — 기존 종료일 다음 날부터는 허용)

질문   PUT으로 사이트/날짜를 바꿔 다른 예약과 겹치게 만드는 경우도 이 티켓에서
       다뤄야 하는가 → updateReservation에는 겹침 체크 자체가 없어 범위가 다르다
       (실측: id=2 A-3 2026-08-31~09-01과 완전히 겹치는 PUT이 200으로 성공).
       T-8로 분리, 이 티켓에서는 판단하지 않는다.
```

```
규칙   취소된(CANCELLED) 예약은 중복 체크에서 제외된다 — 같은 사이트·같은
       기간에 CANCELLED 예약만 있다면 겹침으로 보지 않고 허용한다.
이유   취소된 예약은 더 이상 자리를 점유하지 않으므로 같은 자리·같은 기간의
       새 예약을 막을 이유가 없다.

Given  기준일 2026-08-17, A-10에 CANCELLED 상태 예약 존재
       (취소 시점이 오늘이 아니었던 예약 — cancelReservation은 시작일이
       오늘이면 CANCELLED_SAME_DAY, 아니면 CANCELLED로 상태를 나눠 저장)
When   POST 취소된 예약과 동일 사이트·동일 기간으로 재예약        Then  (버그) 409로 거부 (신고 증상 재현) → 기대 201

질문   CANCELLED_SAME_DAY(당일 취소)도 이 규칙에 포함해 재예약을 허용해야
       하는가 → 당일 취소 직후 즉시 재예약을 허용할지는 노쇼 방지·위약금
       정책과 얽힐 수 있어 요구사항이 침묵한다. 현재 동작(재예약 불가, 409)
       그대로 유지 (실측: A-11 당일 취소 후 재예약 시도 409로 동일하게 막힘).
       T-9로 분리, 이 티켓에서는 CANCELLED만 다룬다.
```
