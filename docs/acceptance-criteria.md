# Top 3 인수 조건 (Acceptance Criteria)

`risk-matrix.md`에서 우선순위가 가장 높게 평가된 Top 3 기능에 대해, 5W1H 분석을 기반으로 인수 조건과 검증 포인트를 정리합니다.

---

## 1. 예약 생성 (중복 예약 방지 포함)

### 5W1H
- **Who (누가)**: 신규 예약자(예: 김철수)
- **What (무엇을)**: 특정 사이트(A-1)의 특정 기간(startDate~endDate)을 예약한다.
- **When (언제)**: 오늘 이후의 미래 날짜(예: 2030-01-10 ~ 2030-01-12)
- **Where (어디서)**: 예약 시스템의 예약 생성 API(`POST /api/reservations`)
- **Why (왜)**: 고객이 원하는 날짜에 캠핑을 예약하고, 시스템은 이중 예약을 방지하여 신뢰성과 데이터 무결성을 보장한다.
- **How (어떻게)**: 예약 요청 시 시스템이 입력값을 검증하고, 동일 사이트/겹치는 기간 예약이 있으면 거부한다.

### 인수 조건 (한 문장)
**인수 조건**: "사용자가 유효한 미래 기간과 필수 정보를 입력해 예약을 생성하면 예약이 저장되고 확인코드가 발급되며, 동일 사이트의 기간이 겹치는 예약은 생성이 거부된다."

### 검증 포인트
- [ ] **필수 입력 검증**: `siteNumber`, `startDate`, `endDate`, `customerName` 누락 시 실패한다.
- [ ] **날짜 규칙**: `endDate < startDate`면 실패한다.
- [ ] **과거 예약 금지**: `startDate < 오늘`이면 실패한다.
- [ ] **기간 제한**: 예약 기간이 정책(30일 이내)을 초과하면 실패한다.
- [ ] **중복 예약 방지**: 동일 사이트에서 기존 예약 기간과 겹치면 실패한다. (겹침 판정 기준 명확화: `startDate~endDate`가 겹치면 실패)
- [ ] **동시성 안전성**: 동시에 동일 기간/사이트로 여러 요청이 들어와도 1건만 성공해야 한다. (현 구현에 취약점이 있으므로 테스트로 드러나야 함)
- [ ] **확인코드 발급**: 성공 시 `confirmationCode`가 6자리 영숫자로 생성된다.
- [ ] **기본 상태**: 성공 시 예약 상태가 `CONFIRMED`로 저장된다.
- [ ] **요구사항 불일치 확인(전화번호)**: 전화번호가 필수인지 정책을 확정하고, 필수라면 누락 시 실패해야 한다.

## 2. 사이트 가용성/기간 검색

### 5W1H
- **Who (누가)**: 예약을 시도하기 전 가용한 사이트를 찾는 사용자(예: 홍길동)
- **What (무엇을)**: 특정 날짜 또는 기간에 예약 가능한 사이트 목록을 조회한다.
- **When (언제)**: 예약하려는 날짜/기간을 정했을 때(예: 2030-01-10 ~ 2030-01-12)
- **Where (어디서)**: 사이트 가용성/검색 API(`GET /api/sites/*`)
- **Why (왜)**: 사용자가 실제로 예약 가능한 사이트만 보고 선택하도록 하여 예약 실패/혼선을 줄이기 위해
- **How (어떻게)**: 시스템이 기존 예약 데이터(기간) 기준으로 가용성을 판단해 결과를 반환한다.

### 인수 조건 (한 문장)
**인수 조건**: "사용자가 조회한 날짜/기간에 대해 시스템은 기존 예약과 충돌하지 않는 사이트만 ‘가용’으로 반환해야 하며, 단일일자/목록/기간검색 API 간 가용성 판단 기준이 일관돼야 한다."

### 검증 포인트
- [ ] **단일일자 가용성**(`/api/sites/{siteNumber}/availability`): 해당 날짜가 어떤 예약의 기간에 포함되면 `available=false`여야 한다.
- [ ] **특정 날짜 가용 사이트 목록**(`/api/sites/available?date=...`): 기간 기준과 동일한 결과를 반환해야 한다(현재 `reservationDate` 기반 혼재를 제거/정의해야 함).
- [ ] **기간 검색**(`/api/sites/search?startDate=...&endDate=...`): 시작~종료까지 **모든 날짜**가 예약 가능해야만 결과에 포함되어야 한다.
- [ ] **중간 날짜 검증**: 시작/종료일만이 아니라, 기간 내 중간 날짜에 예약이 있으면 결과에서 제외된다.
- [ ] **과거 검색 금지**: `startDate < 오늘`이면 검색이 실패한다.
- [ ] **기간 논리 검증**: `endDate < startDate`이면 검색이 실패한다.
- [ ] **size 필터 동작**: `size=대형/소형/일반` 필터가 정확히 적용된다(정의된 분류 규칙 포함).

## 3. 예약 수정

### 5W1H
- **Who (누가)**: 기존 예약을 변경하려는 예약자(예: 김철수)
- **What (무엇을)**: 날짜/사이트/예약자 정보 등 예약 일부를 변경한다.
- **When (언제)**: 예약 변경이 필요할 때(단, 정책상 허용되는 범위 내)
- **Where (어디서)**: 예약 수정 API(`PUT /api/reservations/{id}`)
- **Why (왜)**: 고객 사정 변경에 대응하고 운영 혼선을 줄이기 위해
- **How (어떻게)**: 확인코드를 통해 본인 확인 후, 변경 요청 값을 검증하고 저장한다.

### 인수 조건 (한 문장)
**인수 조건**: "예약자는 올바른 확인코드를 제시하면 예약을 수정할 수 있으며, 변경된 날짜/사이트가 정책을 만족하고 다른 예약과 충돌하지 않을 때만 수정이 반영된다."

### 검증 포인트
- [ ] **본인 확인 필수**: `confirmationCode` 누락 또는 불일치 시 수정이 거부된다.
- [ ] **부분 업데이트**: 전달된 필드만 변경되고, 미전달 필드는 기존 값이 유지된다.
- [ ] **날짜 규칙**: `endDate < startDate`면 실패한다.
- [ ] **과거 예약 금지**: 수정 후 `startDate < 오늘`이면 실패한다.
- [ ] **기간 제한**: 수정 후 예약 기간이 30일 제한을 초과하면 실패한다. (현재 구현 누락 → 인수 조건으로 명시)
- [ ] **중복 예약 방지**: 수정 후 기간/사이트가 기존 다른 예약과 겹치면 실패한다. (현재 구현 누락 → 인수 조건으로 명시)
- [ ] **사이트 존재 검증**: 변경하려는 `siteNumber`가 존재하지 않으면 실패한다.

---

## 비고(현행 구현과의 대표 불일치)
- 예약 생성과 예약 수정에서 검증 규칙(30일 제한, 중복 예약 방지)이 일관되지 않습니다.
- 사이트 가용성 로직이 `reservationDate` 기반과 기간 겹침 기반으로 혼재돼 있습니다.
- 전화번호 필수 여부가 요구사항과 구현이 불일치합니다.
