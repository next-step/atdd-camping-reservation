# 리스크 매트릭스 (Risk Matrix)

본 문서는 `SYSTEM_ANALYSIS_REPORT.md`에서 정리된 리스크와 실제 코드 구현(예약/사이트/캘린더 서비스)을 다시 대조해, 기능별 리스크를 정량화한 결과입니다.

## 평가 기준
- **척도**: 높음(3점), 보통(2점), 낮음(1점)
- **계산식**: 리스크 점수 = 비즈니스 임팩트 + 변경 빈도 + 버그 가능성

### 점수 산정 가이드(이번 프로젝트에 적용한 기준)
- **비즈니스 임팩트**
  - 3: 매출/핵심 고객경험/서비스 신뢰에 직접 영향(예약 생성/취소 등)
  - 2: 주요 기능이지만 대체/우회 가능(검색/조회 등)
  - 1: 부가 기능 또는 운영 영향이 제한적
- **변경 빈도**
  - 3: 요구사항 변경/개선 가능성이 높거나(ATDD 대상), 코드가 비대한 영역(리팩토링 가능성↑)
  - 2: 기능 확장 가능성은 있으나 빈번하진 않음
  - 1: 안정화되어 변경 가능성이 낮음
- **버그 가능성**
  - 3: 동시성/데이터 정합성/검증 누락/로직 불일치가 명확(근거 존재)
  - 2: 잠재 이슈는 있으나 영향 범위 제한 또는 방어 로직 일부 존재
  - 1: 단순 조회/정적 화면 수준

## Top 3 선정 근거

1. **예약 생성 (9점)**
   - **비즈니스 임팩트(3)**: 예약은 서비스의 핵심 트랜잭션이며 매출/운영과 직결됩니다.
   - **변경 빈도(3)**: 요구사항(`requirements.md`)과 구현 불일치(전화번호 필수 등)가 이미 존재하고, 레거시 서비스가 거대(`ReservationService` 1000+ 라인)하여 개선/리팩토링 가능성이 큽니다.
   - **버그 가능성(3)**: 중복 예약 방지는 `exists` 체크 후 `save` 패턴이며, **의도적으로 `Thread.sleep(100)`이 포함**되어 TOCTOU 경쟁 조건이 매우 쉽게 발생합니다.

2. **사이트 가용성/기간 검색 (8점)**
   - **비즈니스 임팩트(3)**: 사용자가 예약 가능 사이트를 잘못 판단하면 예약 실패/불만/CS로 이어집니다.
   - **변경 빈도(2)**: 추가 필터(전기, 인원, 가격 등) 요구가 자연스럽고 변경 가능성이 중간 이상입니다.
   - **버그 가능성(3)**: 가용성 판단이 API별로 **기간 기준 vs `reservationDate` 기준**으로 혼재합니다.
     - `/api/sites/search`는 시작일/종료일만 체크해 **중간 날짜 예약을 놓칠 수 있는 구조적 결함**이 있습니다.

3. **예약 수정 (7점)**
   - **비즈니스 임팩트(3)**: 예약 정보 변경은 고객 경험/운영에 직접 영향이 큽니다.
   - **변경 빈도(2)**: 정책(수정 가능 기간, 변경 수수료 등) 추가가 흔합니다.
   - **버그 가능성(2)**: 확인코드 검증은 있으나,
     - 업데이트 시 **중복 예약(기간 겹침) 체크가 없고**
     - **30일 제한도 적용되지 않아** 예약 생성 규칙과 불일치가 발생할 수 있습니다.

## 참고(근거가 된 코드/문서 포인트)

- 동시성 재현 지점: `ReservationService#createReservation` 내부 `Thread.sleep(100)`
- 중복 예약 체크: `existsByCampsiteAndStartDateLessThanEqualAndEndDateGreaterThanEqual(...)`
- 가용성 로직 혼재:
  - 기간 기준: `SiteService#isAvailable` (start/end 겹침)
  - reservationDate 기준: `SiteService#getAvailableSites`, `SiteService#searchAvailableSites`, `CampsiteService#isAvailable`
- 조회/캘린더/통계의 성능 위험: 다수 메서드에서 `reservationRepository.findAll()` 이후 메모리 필터링
- 요구사항 원문: `requirements.md`
