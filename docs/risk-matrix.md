# 리스크 매트릭스

## 평가 기준
- **척도**: 높음(3점), 보통(2점), 낮음(1점)
- **계산식**: 리스크 점수 = 비즈니스 임팩트 + 변경 빈도 + 버그 가능성

### 평가 기준 상세
- **비즈니스 임팩트**: 기능 장애 시 매출/고객 신뢰에 미치는 영향
  - 높음(3): 매출 직결, 고객 이탈 가능
  - 보통(2): 불편하지만 대체 수단 존재
  - 낮음(1): 영향 제한적
- **변경 빈도**: 해당 기능의 데이터 조작 방식에 따른 위험도
  - 높음(3): 데이터 생성/삭제 - 오류 시 전체 시스템에 영향
  - 보통(2): 데이터 수정 - 기존 데이터 변경
  - 낮음(1): 데이터 조회 - 읽기 전용
- **버그 가능성**: system-analysis 분석을 통해 발견된 버그 건수로 평가.
  - 2건 이상 = 높음(3)
  - 1건 = 보통(2)
  - 0건 = 낮음(1)

## Top 3 선정 근거

### 1. 예약 생성 (9점)

**비즈니스 임팩트: 높음(3)**
- 캠핑장의 핵심 수익 창출 기능으로 매출과 직결
- 예약 실패 시 고객 이탈 및 매출 손실 발생

**변경 빈도: 높음(3)**
- 가격 정책(주말/성수기 할증) 변경 가능성 높음
- 포인트 적립률, 검증 규칙 등 비즈니스 요구사항 변경 빈번

**버그 가능성: 높음(3)**
- **발견된 버그**: 취소된 예약(CANCELLED)이 중복 체크에서 제외되지 않음 (`ReservationService:137-141`)
- **발견된 버그**: 30일 제한이 "오늘로부터 30일"이 아닌 "예약 기간 30일"로 잘못 구현
- 100줄 이상의 긴 메서드, 깊은 중첩(4단계)으로 복잡도 높음

---

### 2. 연박 예약 (8점)

**비즈니스 임팩트: 높음(3)**
- 장기 예약은 단가가 높아 매출에 큰 영향
- 연박 고객은 충성 고객일 가능성 높음

**변경 빈도: 보통(2)**
- 연박 할인 정책 등 추가 가능성 있음
- 기본 로직은 비교적 안정적

**버그 가능성: 높음(3)**
- **Critical 버그 발견**: `SiteService:101-106`에서 시작일과 종료일만 검사하고 **중간 날짜는 검사하지 않음**
```java
// 현재 코드 - 중간 날짜 검증 누락
boolean startAvailable = !reservationRepository.existsByCampsiteAndReservationDate(site, request.getStartDate());
boolean endAvailable = !reservationRepository.existsByCampsiteAndReservationDate(site, request.getEndDate());
// 중간 날짜(예: 3박 4일 중 2,3일차)는 검사 안함!
```
- 예: 1/1~1/3 예약이 있는데 1/1~1/5 연박 예약이 가능하게 됨

---

### 3. 가용성 확인 (8점)

**비즈니스 임팩트: 높음(3)**
- 예약 가능 여부 판단의 기초가 되는 핵심 기능
- 잘못된 가용성 정보는 중복 예약 또는 빈 사이트 발생

**변경 빈도: 보통(2)**
- 가용성 판단 기준 변경 가능 (예: 정비일 제외 등)
- 필터링 옵션 추가 가능성

**버그 가능성: 높음(3)**
- **발견된 버그**: API 간 일관성 없는 쿼리 사용
  - `getAvailableSites`: `existsByCampsiteAndReservationDate` (단일 날짜 필드)
  - `isAvailable`: `existsByCampsiteAndStartDateLessThanEqualAndEndDateGreaterThanEqual` (기간)
- **발견된 버그**: 연박 검색 시 중간 날짜 미검증 (연박 예약과 동일 문제)
- 취소된 예약이 가용성 계산에서 제외되지 않음
