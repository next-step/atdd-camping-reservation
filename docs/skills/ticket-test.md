# ticket-test — 2. 인수 테스트

`acceptance-criteria.md`의 규칙을 겨눈, 지금은 실패하는 테스트를 세운다. `plan.md` 2단계를 실행한다.

## 읽는 것

- `docs/acceptance-criteria.md` (이번 티켓 섹션)
- `docs/test-guide.md` — **제약 전부. 초안은 이 가이드를 그대로 따른다.**
- `src/test/java/com/camping/legacy/` 기존 인수 테스트 (클래스 스타일과 점유한 사이트)

## 하는 일

1. 초안을 만든다. 지시는 다섯 줄이 고정이다 (T-1·T-2에서 두 번 재사용돼 굳혔다):
   - "`acceptance-criteria.md`의 규칙 하나에 테스트 하나를 붙여라. 테스트 이름에 규칙 번호를 넣어라."
   - "경계는 양쪽을 단언해라. 통과하는 값과 거부되는 값을 각각 하나씩."
   - "이번 티켓에서 새로 넣는 규칙의 테스트는 **지금 실패해야 한다**. 기존 동작 규칙은 지금 통과해야 한다."
   - "확정되지 않은 것은 단언하지 마라. 문구가 미정이면 상태 코드만 본다."
   - "제약은 `test-guide.md`를 먼저 읽고 그대로 따라라."
2. 초안을 `test-guide.md` "초안을 어떻게 판정하는가"의 눈으로 판정한다.
   어긋나면 제약으로 말해 다시 받고, **그 제약을 가이드에 한 줄 추가한다.**
3. 실행한다: `./gradlew test --rerun-tasks`.
   - 새 규칙 테스트는 지금 실패해야 한다. 실패 **사유**가 단언 실패인지
     `build/test-results/test/*.xml`에서 확인한다.
   - 기존 동작 규칙과 이전 티켓의 테스트는 전부 통과해야 한다.
4. 여기서 코드를 고치지 않는다.

## 남기는 것

- 실패하는 새 테스트 (티켓별 클래스, `Reservation<규칙>AcceptanceTest`)
- `docs/test-guide.md`: 이번에 새로 말해야 했던 제약 (한 줄씩)
- 커밋 1개 — `T-n 인수 테스트 추가: AC-n이 지금 실패하는 것을 확인`. 실패 개수·사유를 본문에.

## 넘어가기 전에 사람이 확인할 것

- 실패 사유가 단언 실패인가 — 컨텍스트 기동 실패·연결 오류면 반려
- 보낸 값·기대 상태 코드가 `acceptance-criteria.md` 예시의 숫자와 같은가
- Q-n(미확정)을 단언하고 있지 않은가
- 새로 말한 제약 수가 지난 티켓보다 줄었는가 — 결과를 `retrospective.md`에 한 줄
