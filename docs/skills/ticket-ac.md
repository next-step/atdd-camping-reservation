# ticket-ac — 1. 인수 조건

티켓 하나를 받아 인수 조건을 확정한다. `plan.md` 1단계를 실행한다.

## 읽는 것

- 티켓(신고문)과 이번 티켓에서 다룰 요구사항
- 신고 증상이 지나가는 코드 (서비스·컨트롤러·리포지토리·엔티티)
- `src/main/resources/data.sql` (시드가 무엇을 점유하는지)
- `docs/tickets.md` (번호 공간: 신고는 T-n, 발견은 F-n, 질문은 Q-n)
- `docs/acceptance-criteria.md` (문서 틀: 티켓 섹션 아래 규칙마다 **규칙·예시·이유**)

## 하는 일

1. 티켓을 `tickets.md`에 T-n으로 등록한다. 신고문과 요구사항을 그대로 옮긴다.
2. 코드에서 지금 동작을 파악하고, 증상의 원인 지점을 `파일:줄`로 특정한다.
3. 경계를 직접 호출해 실측한다.
   - 서버: `./gradlew bootRun` 백그라운드. 8080이 이미 응답하면 **옛 프로세스일 수 있다** —
     예약 개수(시드 5건)로 새 인스턴스인지 확인하고, 아니면 `netstat -ano`로 PID를 찾아 내린다.
   - 사이트는 시드(`data.sql`)와 기존 테스트가 점유한 것을 피해서 고른다.
     점유 목록은 `test-guide.md` "어떻게 격리하는가"에 있다.
   - 요구사항의 "없음/필수"는 형태 전부(필드 누락·빈 문자열·공백만)를 잰다 — 서로 다른 요청이다.
   - 규칙에 상태(state)가 끼면 그 상태의 전체 값 목록을 코드에서 먼저 확인하고, 값마다 실측한다.
     (T-3: 취소 상태가 CANCELLED 하나가 아니라 CANCELLED_SAME_DAY도 있었다.)
   - 경계는 양쪽을 잰다: 통과해야 하는 값 하나, 거부돼야 하는 값 하나.
4. `acceptance-criteria.md`에 티켓 섹션을 쓴다. 규칙(AC-n)마다 **규칙·예시·이유**.
   예시는 방금 받은 실제 응답만 쓴다. 바뀌어야 할 동작은 "현재 실측 → / 이 티켓 이후 →"로 나눈다.
5. 이번 구현이 스칠 기존 동작은 "(기존 동작, 유지)" 규칙으로 못을 박는다 — 회귀 기준이 된다.
6. 요구사항에 없는데 코드가 강제하는 규칙, 같은 뿌리의 다른 구멍(수정·조회 경로)을 만나면
   F-n으로 **등록만** 한다. 이번 티켓에서 고치지 않는다.
7. 사양 없이 정할 수 없는 것은 Q-n으로 남기고 "무엇이 확인되면 정리되는가"를 적는다.

## 남기는 것

- `docs/tickets.md`: T-n 등록, 발견한 F-n
- `docs/acceptance-criteria.md`: AC-n(규칙·예시·이유), Q-n
- 커밋 1개 — `T-n 인수 조건 확정: <규칙 한 줄>`. 실측 요약과 Q-n 목록을 본문에.

## 넘어가기 전에 사람이 확인할 것

- 예시가 전부 직접 호출해 받은 응답인가 — 지어낸 값이 없는가
- 규칙이 신고문·요구사항의 올바른 읽기인가 — 다르게 읽을 여지는 Q-n으로 남겼는가
- F-n으로 뺀 것이 정말 이번 티켓 밖인가
