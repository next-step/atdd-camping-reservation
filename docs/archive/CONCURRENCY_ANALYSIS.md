# 예약 시스템 동시성 문제 분석 및 해결 방안

## 1. 문제 현상 정의

현재 캠핑장 예약 시스템의 `createReservation` 로직에는 동시성 제어가 없어 Race Condition(경쟁 상태)에 취약합니다. 두 명 이상의 사용자가 거의 동시에 동일한 날짜에 동일한 캠핑 사이트를 예약할 경우, 다음과 같은 문제가 발생할 수 있습니다.

- **시나리오:**
  1. **사용자 A**가 특정 사이트와 날짜의 예약 가능 여부를 확인합니다. (가능)
  2. **사용자 B**가 거의 동시에 동일한 사이트와 날짜의 예약 가능 여부를 확인합니다. (여전히 가능, 아직 사용자 A의 예약이 완료되지 않음)
  3. **사용자 A**가 예약을 생성하고 데이터베이스에 저장합니다.
  4. **사용자 B**가 예약을 생성하고 데이터베이스에 저장합니다.

- **결과:**
  - 시스템은 두 개의 예약을 모두 유효한 것으로 처리하여 **중복 예약(Double Booking)** 이 발생합니다.
  - 또는 마지막에 저장한 예약만 유효하게 처리되어 먼저 요청한 사용자의 예약이 누락되는 **덮어쓰기(Last-Write-Wins)** 문제가 발생할 수 있습니다.

## 2. 동시성 제어 전략 비교

이 문제를 해결하기 위해 데이터베이스 트랜잭션 레벨에서의 락(Lock) 메커니즘을 도입할 수 있습니다. 대표적인 두 가지 전략은 다음과 같습니다.

### 가. 비관적 락 (Pessimistic Lock)

- **동작 방식:** 데이터에 접근할 때부터 `SELECT ... FOR UPDATE`와 같은 쿼리를 사용하여 해당 레코드에 배타적인 락을 겁니다. 트랜잭션이 종료될 때까지 다른 트랜잭션은 해당 레코드에 접근할 수 없습니다.
- **장점:** 데이터 정합성을 확실하게 보장합니다.
- **단점:**
    - 락을 유지하는 시간이 길어져 전체 시스템의 처리량(Throughput)이 감소할 수 있습니다.
    - 사용자가 실제로 예약을 완료하지 않고 페이지를 떠나는 경우에도 불필요하게 락이 유지될 수 있습니다.
    - 락 경합이 심한 경우 데드락(Deadlock) 발생 가능성이 있습니다.

### 나. 낙관적 락 (Optimistic Lock)

- **동작 방식:** 데이터베이스 레코드 자체에 락을 걸지 않고, 대신 `version`과 같은 버전 관리 컬럼을 둡니다. 데이터를 수정할 때, 이전에 읽었던 버전과 현재 데이터베이스의 버전이 일치하는지 확인합니다. 일치하지 않으면 다른 트랜잭션에 의해 데이터가 변경된 것이므로 현재 트랜잭션을 롤백하고 예외를 발생시킵니다.
- **장점:**
    - 실제 데이터 충돌이 발생할 때만 롤백하므로, 락으로 인한 성능 저하가 거의 없습니다.
    - 대부분의 요청이 충돌 없이 성공하는 웹 애플리케이션 환경(예: 예약 시스템)에 더 적합합니다.
    - 비관적 락에 비해 구현이 간단하고 데드락 위험이 없습니다.
- **단점:**
    - 충돌이 자주 발생하는 환경에서는 롤백 및 재시도 처리 비용이 비관적 락보다 클 수 있습니다. (하지만 예약 시스템에서는 충돌 빈도가 낮을 것으로 예상)

## 3. 제안 해결 방안: 낙관적 락 도입

요청해주신 내용과 같이, 현재 시스템의 특성을 고려했을 때 **낙관적 락**을 도입하는 것이 가장 합리적인 해결책입니다.

- **이유:**
    - 예약 시스템은 읽기 작업이 쓰기 작업보다 훨씬 빈번합니다.
    - 두 명의 사용자가 정확히 같은 시간에 같은 사이트를 예약하려는 충돌 상황은 드물게 발생할 것으로 예상됩니다.
    - 따라서 비관적 락으로 인한 성능 저하를 감수하는 것보다, 충돌 발생 시 사용자에게 재시도를 유도하는 방식(낙관적 락)이 전체적인 사용자 경험과 시스템 성능에 더 유리합니다.

- **구현 계획:**
    1. `Reservation` 엔티티에 버전 관리를 위한 `@Version` 어노테이션이 달린 `version` 필드를 추가합니다.
    2. `createReservation` 서비스 메소드에서 `OptimisticLockException` 발생 시, 이를 처리하여 사용자에게 "이미 예약이 완료되었거나 예약 정보가 변경되었습니다. 다시 시도해주세요."와 같은 적절한 메시지를 반환하도록 예외 처리 로직을 구현합니다.
