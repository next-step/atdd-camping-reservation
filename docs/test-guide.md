# 테스트 가이드

테스트 초안에 주는 제약. 규칙 한 줄씩 쌓는다.
지시 문장 자체는 `plan.md`의 "AI에게 주는 지시" 칸에 있다.

## 무엇을 단언하는가

- 규칙 하나에 테스트 하나. 테스트 이름에 인수 조건 번호(AC-n)를 넣는다.
- 경계는 양쪽을 단언한다. 통과하는 값 하나와 거부되는 값 하나를 붙여 쓴다.
- 확정되지 않은 것은 단언하지 않는다. 문구가 미정이면 상태 코드만 본다. (T-1 AC-1)
- 확정된 문구는 단언한다. 실측으로 받아 `acceptance-criteria.md`에 적힌 문구만 해당한다.
- 필수 위반의 "없음"은 세 형태를 각각 단언한다: 필드 누락, 빈 문자열, 공백만. 누락은 JSON에서 키를 빼서 재현한다 — null을 넣는 것과 다른 요청이다. (T-2 AC-4)
- 여러 걸음을 순서로 밟는 테스트는 걸음마다 단언한다. 마지막 걸음만 보면 앞 걸음의 조용한 실패가 원인을 가린다. (T-3 AC-6: 생성 201 → 취소 200 → 상태 확인 → 재예약 201)
- 이번 티켓에서 새로 넣는 규칙의 테스트는 실행하면 지금 실패해야 한다. 실패 이유가 단언 실패인지(설정 오류가 아닌지) 리포트에서 확인한다.

## 어떻게 격리하는가

- HTTP 경계로만 검증한다. 서비스·리포지토리를 직접 부르지 않는다. 인수 조건의 예시가 HTTP 응답이라 단언 대상도 같아야 한다.
- 날짜는 `LocalDate.now()` 기준 상대값으로 잡는다. 고정 날짜를 쓰지 않는다. `data.sql`이 `DATEADD(..., CURRENT_DATE)`로 시드를 넣어 오늘이 바뀌면 고정 날짜가 깨진다.
- 테스트마다 다른 사이트를 쓴다. `@SpringBootTest` 컨텍스트 하나를 공유해 DB가 테스트 사이에 이어지고, 예약 충돌 검사에 서로 걸린다.
- 시드 예약이 있는 사이트는 피한다. `data.sql`이 `A-1`·`A-2`·`A-3`·`A-4`·`A-6`에 예약을 넣어 둔다.
- 사이트 점유 현황 (테스트가 새 사이트를 쓰면 여기 갱신한다):
  - 시드: A-1~A-4, A-6
  - ReservationDateRuleAcceptanceTest: A-10~A-14
  - ReservationPhoneRuleAcceptanceTest: B-11~B-14
  - ReservationConflictRuleAcceptanceTest: A-15~A-17

## 초안을 어떻게 판정하는가

답하려는 질문은 하나다 — "이 테스트가 통과하면 규칙이 지켜진 것인가."
찾는 것은 **거짓 통과**(규칙이 깨졌는데 통과)와 **거짓 실패**(규칙은 멀쩡한데 설정 오류로 실패)다.

눈으로 보는 것:

- 테스트 개수가 인수 조건 개수와 맞고, 이름에 AC 번호가 있다.
- 테스트에서 **보낸 값**과 **기대한 상태 코드**가 `acceptance-criteria.md` 예시의 숫자와 같다.
- 대조할 때 값을 둘로 나눈다. 규칙을 이루는 값(경계 숫자·상태 코드·문구)은 같아야 하고, 아무거나 되는 값(사이트 번호·이름·전화번호)은 달라도 된다. 다르면 왜 다른지 설명이 돼야 한다.
- 질문으로 남긴 것(Q-n)을 단언하고 있지 않다. 정하지 않은 것을 테스트가 굳히면 반려한다.

돌려서 보는 것:

- 새 규칙의 테스트가 지금 실패한다.
- 실패 **사유**가 단언 실패다. 연결 오류·예외·컨텍스트 기동 실패면 규칙과 무관하므로 반려한다.
- 통과하는 테스트는 값을 일부러 틀리게 바꿔 **실패하는지** 본다. 안 바뀌면 그 단언은 아무것도 잡지 않는 빈 껍데기다.
- 구현 전에는 "통과해야 하는 새 규칙 테스트"가 무엇을 넣어도 통과할 수 있다. 규칙이 없어 전부 통과하기 때문이다. 이 테스트의 고장내기는 **구현 후 4단계에서 다시 한다.**
