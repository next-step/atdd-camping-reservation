# 요청은 실측과 같은 모양으로 보낸다

`acceptance-criteria.md`의 실측과 같은 층에서, 같은 경로와 같은 필드 집합으로 보낸다.
실측에 없던 필드를 테스트가 새로 만들거나, 실측이 채운 필드를 빼지 않는다.

이유 — 인수 조건의 예시가 curl로 적혀 있다. 테스트가 그것과 다른 요청을 보내기 시작하면
테스트는 통과하는데 실제 호출은 실패하는 자리가 생긴다.

# 프로덕션 타입을 쓰지 않는다

인수 테스트는 요청을 맵으로 만들고, 응답을 필드 이름으로 읽는다.

이유 — 인수 테스트는 그 움직임이 겉보기 행동을 바꿨는지 판정하는 쪽이어야 한다.
프로덕션 타입을 함께 쓰면 타입이 바뀔 때 테스트도 따라 바뀌어, 행동이 그대로인지 판정할 수 없다.

# 값의 부재는 셋으로 나눈다

필드를 넣지 않은 것, null 을 넣은 것, 빈 값을 넣은 것을 한 케이스로 묶지 않는다.
호출부에 각각을 보낼 수 있는 자리를 두고, 테스트는 셋을 따로 단언한다.

이유 — 셋은 서로 다른 요청 본문으로 나간다. 
하나로 묶으면 나머지 둘이 통과하는지 모른 채 통과로 읽힌다.

# 거절 뒤 상태까지 단언한다

상태 코드와 메시지 전문에 더해,
남지 않아야 할 것이 남지 않았는지 바뀌지 않아야 할 것이 그대로인지를 조회로 본다.

이유 — 상태 코드만 보면 거절해 놓고 저장하는 경우를 놓친다.

# When 은 호출만 하고, 통과 기준은 테스트가 정한다

When 을 보내는 공통 호출부는 요청만 보내고 응답을 그대로 돌려준다.
무엇을 통과로 볼지는 그 응답을 받은 테스트가 정한다.

이유 — 호출 쪽이 상태 코드를 단언하면 티켓마다 다른 통과 기준을 걸 수 없다.

# Given 은 호출과 단언을 함께 한다

준비 호출은 자리가 섰는지까지 그 안에서 단언하고, 응답 코드만으로 섰는지 알 수 없으면 조회로 확인한다.

이유 — 여러 걸음을 순서로 밟는 테스트에서 앞 걸음이 조용히 무너지면,
뒤 걸음의 실패를 신고된 증상으로 잘못 읽는다. 준비가 무너져서 난 실패는 증상 재현이 아니다.

# 겹침은 날짜가 아니라 사이트로 피한다

테스트끼리 예약이 부딪힐 때 시작일을 멀리 밀어 피하지 않는다. 사이트를 다르게 잡는다.
`data.sql` 의 시드 예약이 이미 잡은 사이트도 함께 피한다.

이유 — 인수 테스트는 실제 서버를 띄우고 HTTP 로 호출한다.
요청을 받은 쪽이 자기 트랜잭션에서 커밋하니 테스트가 만든 예약은 롤백되지 않고 다음 테스트까지 남는다.
