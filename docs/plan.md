# 작업 계획

티켓 하나를 처리하는 순서다. 지켜야 하는 것은 `principles.md`에 있다.

이 순서를 실행하는 형태로 옮긴 것이 스킬이다. 단계 하나가 스킬 하나다.
**두 파일이 어긋나면 계획 쪽도 함께 고친다.**

## 1. 인수 조건 — `/atdd-1-criteria`

- 입력: 티켓, 이 티켓에서 다룰 요구사항, `principles.md`, 앞 티켓이 세운 `acceptance-criteria.md`
- 하는 일: 코드에서 지금 동작을 파악하고, 요구사항과 어긋나는 자리를 판정한다
- 남기는 것: `acceptance-criteria.md`에 규칙과 예시와 이유. 못 정한 것은 질문으로, 남은 일은 `tickets.md`에.
  커밋 `docs: T-N 인수 조건 확정과 발견 티켓 등록`
- 넘어가기 전에: 예시가 직접 호출해 받은 응답인지 확인한다
- AI에게 주는 지시:
  - 요구사항이 침묵하는 자리를 만나면 답을 만들지 말고 선택지로 물어본다. 선택지마다 경계 시나리오가 어떻게 달라지는지 함께 보인다.
  - 경계는 직접 호출해 실측한다.
  - 인수 조건은 시나리오로 쓴다. 규칙마다 실측 응답과 이유를 붙인다. 아직 실패하는 규칙은 "지금 응답"과 "기대 응답"을 나눠 적는다.
  - 지금도 통과하는 동작 중 이번 변경으로 깨질 수 있는 것을 회귀 규칙으로 함께 적는다.
  - 티켓은 요구사항과 API 스펙으로 쓴다. 코드 세부는 넣지 않는다.
  - 티켓은 받은 것과 발견한 것이 같은 구조를 쓴다. 아직 정하지 않은 칸도 비우지 않고 "정해지지 않았다"로 적는다. 형식은 스킬이 갖고 있다.
  - 요구사항에 없는데 코드가 강제하는 규칙을 만나면 티켓으로 등록만 하고 이번 티켓에서 처리하지 않는다. 발견 경위와 "무엇이 확인되면 정리되나"를 함께 적는다.

## 2. 인수 테스트 — `/atdd-2-test`

- 입력: `acceptance-criteria.md`, `test-guide.md`
- 하는 일: 테스트 초안을 받아 규칙을 검증하는지 판정하고 실행한다
- 남기는 것: 테스트 코드, 커밋 `test: T-N ... 인수 테스트 추가`.
  초안에 준 제약은 `test-guide.md`에 규칙 한 줄로
- 넘어가기 전에: 인수 테스트가 지금 실패하는지 확인한다. 실패하지 않으면 지금 동작을 겨눈 초안이다
- AI에게 주는 지시:
  - 초안을 내놓기 전에 무엇을 단언했는지, 무엇으로 실행했는지, 어떻게 격리했는지를 먼저 밝힌다.
  - 실행만 하고 고치지 않는다. 실패가 신고된 증상과 같은 이유인지 실패 메시지로 확인해 보인다.
  - `test-guide.md`는 쓰지 않는다. 규칙이 될 자리만 짚고 넘긴다.

## 3. 구현 — `/atdd-3-implement`

- 입력: 실패하는 인수 테스트, `code-guide.md`
- 하는 일: 그 테스트를 통과시키는 최소 변경
- 남기는 것: 코드, 커밋 `feat: T-N ... 적용`
- 넘어가기 전에: 실패하던 인수 테스트가 통과하는지 확인한다
- AI에게 주는 지시:
  - `code-guide.md`의 규칙을 지키고, 지킨 자리를 코드의 어디인지로 짚어 보인다.
  - 인수 조건이나 테스트를 고쳐서 통과시키지 않는다. 테스트가 틀렸다고 판단되면 2단계로 돌려보낸다.

## 4. 판정 — `/atdd-4-verify`

- 입력: 바뀐 코드, 쌓인 테스트 전부
- 하는 일: 이 티켓이 끝났는지 판정한다. 바뀐 코드를 읽고, 쌓인 테스트를 전부 돌려 회귀를 확인한다
- 남기는 것: 발견한 것이 있으면 `tickets.md`에. 겪은 것은 `retrospective.md`에. 문서가 바뀌었으면 커밋
- 넘어가기 전에: 요구사항대로 됐고 원래 되던 것이 안 깨졌는지 확인한다
- AI에게 주는 지시:
  - 이번 티켓 테스트만 돌리지 않는다. 쌓인 테스트를 전부 돌린다.
  - 처리하지 않기로 한 티켓을 슬쩍 처리하지 않았는지 변경 전체를 읽고 확인한다.
  - 겪은 것을 `retrospective.md`에 적는다. 다음 티켓에서 안 겪고 싶은 것만 적고,
    절차로 굳힐 후보인지 표시한다. 두 번째 겪은 것만 굳힌다.

## 이 저장소의 실행 방법

- 서버 기동: `./gradlew bootRun`, 8080 포트. 8080이 쓰이면 `SERVER_PORT=8081 ./gradlew bootRun`
- 호출할 수 있는 것은 `/api` 아래에 있다
- 샌드박스에서 `bootRun`이 tmpdir 권한으로 죽으면 `./gradlew bootJar` 후 `java -Djava.io.tmpdir=$TMPDIR -jar build/libs/*.jar`로 띄운다
- 테스트 실행: `./gradlew test`. 결과 줄이 안 보이면 캐시다. `./gradlew test --rerun-tasks`로 다시 돌린다
- 실측 전에 포트가 비었는지 본다: `lsof -nP -iTCP:8080 -sTCP:LISTEN`. 이미 떠 있으면 이전 세션의 낡은 코드다.
  그 응답을 실측으로 쓰면 판정이 거짓이 된다. 빈 포트로 옮겨 띄운다
- 데이터를 다루기 전에 `src/main/resources/data.sql`을 읽는다

테스트를 어떻게 짤지도, 코드를 어떻게 쓸지도 이 파일에 적지 않는다.
작업하며 정해 `test-guide.md`와 `code-guide.md`에 쌓는다.

## AI에게 주는 지시 칸

단계마다 마지막 줄이 비어 있다. 그 단계에서 AI에게 실제로 준 지시 중 다시 쓸 만한
것을 적는 자리다. 프롬프트 전문을 옮기지 않고, 다음에도 그대로 쓸 문장만 남긴다.

두 번째 티켓에서 같은 지시를 또 하게 되면 그것이 굳힐 자리다. 네 칸에 쌓인 것이
스킬을 만들 때의 재료가 된다.
