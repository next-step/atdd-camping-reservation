내용: 고객센터 신고 — "오늘로부터 30일 넘게 남은 날짜인데 예약이 됩니다."

T-2 전화번호 형식 제한 / 미입력 시 예약 완료 (요구사항에 없음, 코드가 강제)
내용: T-1 작업 중 `ReservationService.createReservation`에서 발견. 전화번호를 입력하면(선택 항목인데도) `-`를 제거한 뒤 10~11자리 숫자가 아니면 "전화번호 형식이 올바르지 않습니다."로 거부한다. 이 자릿수 기준이 어디서 온 것인지, 하이픈 포함 다른 형식(국제번호 등)은 어떻게 되는지 확인 필요.
추가 신고: 고객센터 신고 — "전화번호를 안 넣었는데 예약이 완료됐습니다." 전화번호 없이도 예약이 완료되는 현재 동작(선택 항목이므로 의도된 것으로 보임)이 실제 요구사항과 맞는지, 필수로 바뀌어야 하는지 확인 필요.

T-4 예약자 이름 길이 제한

T-5 숙박 기간 최대 30일 제한 (요구사항에 없음, 코드가 강제)
내용: T-1 작업 중 발견. `startDate`~`endDate` 사이 숙박 일수가 30일을 넘으면 "예약 기간은 최대 30일입니다."로 거부한다. T-1이 다루는 "오늘로부터 30일"과는 별개의 규칙인데 숫자가 같아 헷갈리기 쉽다. 이 제한이 실제 요구사항인지 확인 필요. (T-1 수정 시 이 규칙과 혼동하지 않도록 주의)

T-6 취소된 예약이 예약 가능 여부 조회에 여전히 "예약됨"으로 잡힘
내용: T-3 작업 중 발견. `ReservationService.checkAvailability`/`checkPeriodAvailability`(`SiteController`가 사용)와 `getMonthlyCalendar`가 예약의 `status`를 보지 않고 레코드 존재 여부만으로 판단한다. `cancelReservation`은 레코드를 지우지 않고 `status`만 `CANCELLED`/`CANCELLED_SAME_DAY`로 바꾸므로, 취소된 예약이 있던 날짜가 예약 가능 여부 조회나 캘린더에서 계속 "예약 불가/예약됨"으로 보일 수 있다. T-3과 근본 원인(취소된 예약을 유효한 예약처럼 취급)은 같지만 별도 API(`checkAvailability`, `getMonthlyCalendar`)이므로 분리해서 확인 필요.

T-7 전화번호 자릿수 기준(10~11자리)의 근거 확인 필요
내용: T-2 작업 중 acceptance-criteria.md에 "T-3"으로 잘못 표기되어 남아 있던 항목을 정정하며 별도 티켓으로 옮김. `-`를 제거한 뒤 10~11자리 숫자가 아니면 거부하는 형식 검증 자체는 유지하기로 했으나(T-2), 이 자릿수 기준이 어디서 온 것인지, 국제번호 등 다른 형식은 어떻게 처리할지는 정해진 바 없다.
