- T-2 범위 조정
  - 처음에는 신규 생성과 예약 변경을 함께 적용하려 했지만, 변경 API는 기존 전화번호 유지와 필수 입력의 의미가 생성 API와 달라 별도 판단이 필요했음. 예약 변경 검증을 T-3으로 분리하면서 T-2를 고객센터 신고가 발생한 신규 생성 문제에 한정할 수 있었음
- T-3에서 AI가 대신 못 한 판단
  - 예약 변경 요청에서 전화번호가 누락되면 기존 번호를 유지할지, 필수값 위반으로 HTTP 400을 응답할지는 기존 코드만으로 결정할 수 없었음. 부분 변경 API의 의미와 전화번호 필수 정책이 충돌하는 지점이라 누락과 `null`도 거부한다는 비즈니스 규칙을 직접 정해야 했음.
- T-3에서 스킬이 못 해 준 부분
  - `atdd-review`에 실측용 선행 요청의 성공 여부를 확인하는 규칙이 없었음. 첫 실측에서 기준 예약 생성이 실패했는데도 응답의 `id`를 사용해 `/undefined`를 호출했음. 각 단계에서 기대 상태 코드와 필수 응답값인 `id`, `confirmationCode`를 확인하고, 실패하면 후속 호출을 중단하도록 실측 절차를 보완할 필요가 있음.
- T-4에서 스킬이 못 해 준 부분
  - `atdd-acceptance`는 범위 밖 문제를 후속 티켓으로 등록하도록 정해 두었지만, 완료 보고에서는 다일 예약의 부분 겹침과 예약 가능 여부·캘린더 조회를 후보로만 남겼음. 재요청 후 T-5와 T-6이 `docs/tickets.md`에 추가함. 후속 범위를 발견하면 인수 조건 문서뿐 아니라 티켓 문서에도 등록됐는지 확인하는 종료 조건이 비어 있었음.
