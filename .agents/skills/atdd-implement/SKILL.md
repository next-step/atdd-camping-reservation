# ATDD 최소 구현

실패하는 인수 테스트를 변경 기준으로 삼아 최소 구현하고, 왜 그 지점만 변경했는지 설명한다.

## 작업 전

1. 적용되는 저장소 지침과 대상 티켓의 범위를 확인한다.
2. 저장소에 있으면 `docs/principles.md`, `docs/plan.md`, 관련 `docs/acceptance-criteria.md`, `docs/test-guide.md`를 읽는다.
3. 대상 인수 테스트를 실행해 Red 상태를 재현한다. 테스트가 실패하지 않으면 구현을 시작하지 말고 기준과 테스트 상태를 보고한다.
4. 실패한 요청의 호출 경로와 원인 코드를 확인한다. 코드의 설명은 가설이며 테스트와 실측 결과를 판정 기준으로 삼는다.
5. 같은 규칙이 적용될 가능성이 있는 유사 지점을 찾아 현재 티켓 범위인지 구분한다.

## 구현

- 실패 원인을 제거하는 최소 프로덕션 변경을 우선한다.
- 인수 테스트나 인수 조건을 약화해 통과시키지 않는다. 기준이 잘못됐다고 판단되면 임의로 수정하지 말고 사용자에게 근거와 함께 알린다.
- 기존 상태 코드, 오류 메시지, 저장 동작 등 현재 티켓과 무관한 행동을 보존한다.
- 유사 지점을 발견해도 현재 인수 조건의 적용 대상이 아니면 함께 고치지 않는다. 필요한 경우 후속 티켓 후보로 남긴다.
- 사용자 변경이 있는 작업 트리에서는 관련 없는 변경을 보존하고 요청 범위의 파일만 수정한다.

## 검증

1. 대상 인수 테스트를 실행해 Green을 확인한다.
2. 저장소가 지정한 전체 테스트를 실행해 회귀를 확인한다.
3. 변경 파일과 diff를 검토해 테스트를 통과시키는 데 필요하지 않은 변경이 없는지 확인한다.
4. 저장소가 직접 실측을 요구하면 구현 전과 같은 경계를 다시 호출하고, 변경 전 기록과 구분해 남긴다.

## 완료 보고

다음 내용을 반드시 포함한다. 파일 목록이나 diff 요약만으로 대신하지 않는다.

- **원인:** 기존 코드가 인수 조건과 어긋난 이유
- **변경:** 어느 지점을 어떻게 바꿨는지
- **범위:** 그 지점을 변경 대상으로 선택한 이유
- **범위 밖:** 확인한 유사 지점과 변경하지 않은 이유
- **검증:** 대상 인수 테스트, 전체 테스트, 필요한 실측 결과
- **남은 일:** 후속 티켓이나 추가 확인 사항

커밋, 푸시 등 별도 저장소 작업은 사용자가 명시적으로 요청했을 때만 수행한다.
