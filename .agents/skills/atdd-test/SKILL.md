# ATDD 인수 테스트

확정된 기준을 실행 가능한 인수 테스트로 옮기고 Red 상태를 증명한다. 이 단계에서는 테스트 대상 프로덕션 코드를 수정하지 않는다.

## 작업 전

1. 적용되는 저장소 지침과 대상 티켓을 확인한다.
2. 저장소에 있으면 `docs/principles.md`, `docs/plan.md`, 관련 `docs/acceptance-criteria.md`, `docs/test-guide.md`를 읽는다.
3. 테스트 데이터가 관련되면 저장소가 지정한 초기 데이터와 설정을 먼저 확인한다.
4. 인수 조건에서 확정되지 않은 기대값을 발견하면 임의로 정하지 않고 질문이나 후속 티켓 후보로 남긴다.

## 테스트 작성

- 각 규칙을 허용 경계와 거부 경계에 연결한다. 문자열 입력은 누락, `null`, 빈 값, 공백, 형식 구간처럼 의미가 다른 동등 분할을 고려한다.
- 외부 인터페이스의 상태 코드와 응답 본문을 검증한다. 거부 요청은 필요한 경우 상태가 변경되거나 데이터가 저장되지 않았는지도 확인한다.
- 현재 시각에 의존하는 경계는 제어 가능한 기준 시각을 사용한다.
- 격리를 위해 의미상 먼 날짜 같은 입력으로 회피하지 않는다. 저장소 가이드에 따라 다른 도메인 객체, 픽스처 초기화, 트랜잭션 또는 SQL을 사용한다.
- 기존 테스트의 구조와 헬퍼를 우선 재사용하되, 인수 조건의 의미가 숨겨지지 않게 한다.
- 사용자가 새로 준 재사용 가능한 테스트 제약은 저장소 지침이 요구할 때 지정된 테스트 가이드에 한 줄로 기록한다.

## Red 확인

1. 저장소가 지정한 명령으로 대상 인수 테스트를 실행한다. 캐시 때문에 실행 여부가 불명확하면 저장소의 재실행 방법을 따른다.
2. 기존에 지원되는 허용 사례는 통과하고, 아직 구현되지 않은 규칙만 의도대로 실패하는지 구분한다.
3. 실패 위치가 인수 조건과 무관하면 테스트나 환경 문제를 먼저 해결한다.
4. 새 테스트가 모두 통과하면 현재 동작을 겨눈 테스트인지 다시 확인하고 결과를 보고한다. 실패를 만들기 위해 기준을 임의로 바꾸지 않는다.

Red 상태를 확인하면 멈춘다. 실패 테스트를 통과시키는 프로덕션 변경은 하지 않는다.

## 완료 보고

다음을 짧게 설명한다.

- 추가한 테스트와 인수 조건의 대응 관계
- 사용한 격리 방법과 기준 시각
- 통과한 사례와 의도대로 실패한 사례
- 테스트 작성에 새로 필요했던 제약
- 구현 단계로 넘길 실패 원인에 대한 관찰. 아직 원인으로 확정하지 않은 내용은 가설로 표시한다.
