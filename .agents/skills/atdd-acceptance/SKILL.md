# ATDD 인수 조건

코드에서 읽은 현재 동작을 가설로 삼고 실제 외부 호출 결과를 근거로 티켓의 통과 조건을 확정한다. 이 단계에서는 인수 테스트와 프로덕션 코드를 작성하지 않는다.

## 작업 전

1. 적용되는 저장소 지침과 대상 티켓을 확인한다.
2. 저장소에 있으면 `docs/principles.md`, `docs/plan.md`, 관련 `docs/acceptance-criteria.md`, `docs/tickets.md`를 읽는다.
3. 데이터가 관련되면 저장소가 지정한 초기 데이터와 실행 방법을 먼저 확인한다.
4. 관련 요청의 컨트롤러, 서비스, DTO, 저장 경로를 읽어 현재 동작에 대한 가설을 세운다. 코드를 판정 근거로 단정하지 않는다.

## 기준 확정

- 티켓에서 다룰 규칙, 적용 범위, 이유를 분리한다.
- HTTP 상태, 오류 메시지, 저장 여부처럼 판정에 필요한 결과를 명시한다.
- 숫자와 날짜는 허용 경계 양쪽을, 문자열은 누락, `null`, 빈 값, 공백, 형식 구간처럼 의미가 다른 동등 분할을 고려한다.
- 요구사항이 침묵하는 값이나 API 범위는 임의로 정하지 않는다. 무엇이 확인되면 결정되는지 질문으로 남긴다.
- 현재 티켓 밖에서 발견한 문제는 함께 구현할 범위로 넓히지 않고 후속 티켓으로 등록한다.

## 직접 실측

1. 다른 규칙의 실패가 섞이지 않도록 나머지 입력은 유효한 기준값으로 고정한다.
2. 격리를 위해 의미상 먼 날짜로 회피하지 않는다. 다른 도메인 객체나 데이터 초기화 등 저장소에 맞는 방법을 사용한다.
3. 외부 인터페이스를 직접 호출해 요청, HTTP 상태, 응답 본문을 수집한다.
4. 거부되어야 하는 요청은 응답만 보지 않고 실제 상태 변경이나 저장 여부도 확인한다.
5. 실제 결과와 기대 결과를 분리해 일치 여부를 판정한다. 실행하지 않은 결과를 실측으로 기록하지 않는다.

## 기록

저장소가 지정한 인수 조건 문서에 다음을 남긴다.

- 규칙과 적용 범위
- 규칙을 정한 이유
- 경계별 요청, 실제 결과, 기대 결과, 판정
- 대표 요청과 원문 응답
- 결정하지 못한 질문과 범위 밖 후속 작업

변경 전 실측과 향후 변경 후 재실측이 혼동되지 않도록 시점을 구분한다. 기록을 마치면 멈추고 테스트나 구현 단계로 넘어가지 않는다.

## 완료 보고

- 확정한 규칙과 적용 범위
- 직접 실측한 경계와 불일치
- 코드에서 읽은 가설 중 실측으로 확인된 내용
- 남은 질문과 후속 티켓 후보
- 아직 직접 확인하지 않은 경계
