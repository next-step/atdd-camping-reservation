# 3. 구현

`docs/principles.md`, `docs/plan.md`를 먼저 읽는다.

## 입력

- 2단계에서 작성한, 지금 레드인 인수 테스트

레드인 인수 테스트가 없으면 진행하지 않는다. 먼저 `/atdd-test <티켓번호>`부터
실행하라고 안내하고 종료한다.

## 하는 일

그 테스트를 통과시키는 최소 변경을 한다.

## AI에게 주는 지시

- 최소한의 변경을 우선한다.
- 구조적 변경(리팩터링, 책임 분리 등)이 필요해 보이면 **곧바로 진행하지 않는다.**
  AskUserQuestion 도구로 왜 필요한지, 어떤 방향으로 할지 사용자에게 직접 묻고
  승인받은 뒤에만 진행한다. 이 확인 없이 구조적 변경을 임의로 하지 않는다.

## 넘어가기 전에 (하드 게이트)

- 구조적 변경이 필요한 지점에서는 AskUserQuestion으로 승인을 받은 뒤에만 코드를 고친다.
- 변경 후 `./gradlew test`로 실패하던 인수 테스트가 통과하는지 실행 결과로 확인하고
  사용자에게 보여준다.
- 변경한 파일과 diff를 나열하는 것으로 끝내지 않는다. 각 변경에 대해 다음을 설명한다:
  - 왜 이 지점을 고쳤는지 (버그의 근본 원인과 이 코드가 그 원인과 어떻게 연결되는지)
  - 무엇을 바꿨는지 (기존 로직 대비 무엇이 달라졌는지, diff만 봐서는 안 드러나는 맥락 포함)
  - 왜 다른 지점은 그대로 뒀는지 (같은 버그처럼 보이지만 범위 밖으로 남긴 곳이 있다면)
  단순 요약이 아니라, 코드를 처음 보는 사람도 diff만으로는 이해하기 어려운 부분을
  이해할 수 있게 하는 설명이어야 한다.

**이 스킬은 여기서 끝난다.** 4단계(판정)는 자동으로 이어서 하지 않는다. 사용자가
`/atdd-verify <티켓번호>`를 직접 호출할 때만 다음 단계가 시작된다는 것을 사용자에게
명시적으로 알리고 턴을 종료한다.
