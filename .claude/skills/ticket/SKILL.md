# 티켓 파이프라인

`docs/plan.md`의 4단계를 순서대로 실행한다. 각 단계의 실제 작업 절차와 "넘어가기 전에" 통과
기준은 **이 스킬이 아니라 각 단계 스킬에 있다**:

- 1단계: `.claude/skills/acceptance-criteria/SKILL.md`
- 2단계: `.claude/skills/acceptance-test/SKILL.md`
- 3단계: `.claude/skills/implementation/SKILL.md`
- 4단계: `.claude/skills/verdict/SKILL.md`

이 스킬은 그 네 스킬을 서브에이전트로 순서대로 실행하고, 사용자 확인 지점(커밋 여부/다음 단계
진행 여부)을 관리하는 역할만 한다. 각 단계의 세부 절차를 이 스킬 안에 다시 적지 않는다 — 절차가
바뀌면 해당 단계 스킬만 고치면 되도록 유지한다.

## 0. 입력 확인

- 인자로 티켓 ID(`T-n`)를 받는다. 시작 단계가 지정되지 않으면 1단계(`acceptance-criteria`)부터
  시작한다.
- 이미 일부 단계가 끝난 티켓일 수 있다(예: `docs/acceptance-criteria.md`에 해당 티켓 블록이 이미
  있거나, `src/test/java`에 관련 테스트 파일이 이미 있음). 그런 흔적이 보이면 어느 단계부터
  시작할지 AskUserQuestion으로 확인한다 — 추측해서 건너뛰지 않는다. 각 단계 스킬의 0단계가 "이전
  단계 미완료"를 자체적으로 감지해 멈추므로, 애매하면 1단계부터 시작해도 안전하다.

## 1. 단계 실행 루프

아래를 1→2→3→4단계 순서로, 바로 앞 단계가 "다음 단계로 진행"으로 확정된 경우에만 반복한다.

### 1-1. 서브에이전트 실행

Agent 도구로 서브에이전트 하나를 **포그라운드로(`run_in_background: false`)** 실행한다 — 다음
질문이 이 결과에 의존하므로 백그라운드로 두고 넘어가지 않는다. `subagent_type`은
`general-purpose`를 쓴다 (Skill/Bash/Edit/Write 도구가 모두 필요하다).

프롬프트에 반드시 담을 내용:

- 지금 처리 중인 티켓 ID와, 이번에 실행할 단계 스킬 이름(`acceptance-criteria` /
  `acceptance-test` / `implementation` / `verdict`), 그 스킬의 `argument-hint`에 맞는 인자.
- "Skill 도구로 `<단계 이름>` 스킬을 호출해 그 SKILL.md의 절차를 처음부터 끝까지 그대로 따르라.
  특히 그 스킬 안의 '넘어가기 전에' 절 조건을 반드시 통과시켜야 한다. (구현 단계 제외) 통과하지
  못하면 스스로 판단해 고치지 말고 왜 막혔는지 보고하고 멈춰라. 구현 단계는 테스트를 통과시킬
  때까지 코드를 고치는 것 자체가 절차이므로 이 예외에서 제외한다."
- "이 스킬의 범위를 벗어나는 행동을 하지 마라 — 다음 단계 스킬을 이어서 실행하지 않는다, 임의로
  커밋하지 않는다, `docs/test-guide.md` 같은 규칙 파일을 조용히 고치지 않고 질문이 필요하면
  AskUserQuestion 대신 응답 텍스트에 그 질문을 적어 돌려준다(서브에이전트는 사용자에게 직접 물을
  수 없다)."
- 반환 형식 지정: 1) 그 단계 스킬의 "마무리 보고" 내용, 2) '넘어가기 전에' 통과 여부와 근거,
  3) 새로 만들었거나 수정한 파일 목록, 4) 판단이 필요해 보류한 질문이 있다면 그 내용.

### 1-2. 사용자에게 보고

서브에이전트가 반환한 요약을 정리해 사용자에게 보여준다. '넘어가기 전에' 조건을 통과하지
못했다면 그 사실을 가장 먼저 알린다. 서브에이전트가 보류한 질문이 있으면 그대로 사용자에게
전달한다.

### 1-3. 게이트 확인

- **통과 못 함**: 다음 단계로 진행하는 옵션을 주지 않는다. 무엇이 막혔는지 보고하고, 어떻게 할지
  AskUserQuestion으로 묻는다(예: 재시도 / 사용자가 직접 개입 후 재실행 / 여기서 중단). 응답을 받을
  때까지 이 단계에 머문다.
- **통과함**: 1-4로 진행한다.

### 1-4. 커밋 여부 확인 — 단계별로 다르게 처리한다

| 단계 | 처리 |
| --- | --- |
| 1 인수 조건 | 산출물이 `docs/*.md`뿐이므로 AskUserQuestion으로 커밋 여부를 묻는다. |
| 2 인수 테스트 | 산출물이 실패하는 테스트 코드(red 상태)뿐이므로 AskUserQuestion으로 커밋 여부를 묻는다. |
| 3 구현 | **커밋 여부를 묻지 않는다.** `docs/plan.md`에서 커밋은 4단계(판정)의 산출물이고, `verdict` 스킬의 0단계는 커밋 안 된 `src/main/java` 변경이 있어야 3단계가 끝났다고 판단한다 — 여기서 먼저 커밋해 버리면 4단계가 3단계 산출물을 못 찾는다. 커밋 없이 다음 단계로 넘어간다고만 안내한다. |
| 4 판정 | `verdict` 스킬이 전체 테스트 통과를 조건으로 이미 커밋까지 수행했다. 별도로 커밋 여부를 묻지 않고, 서브에이전트가 보고한 커밋 해시와 포함 파일을 그대로 전달한다. 스킬이 회귀를 발견해 커밋 없이 멈췄다면, 3단계로 되돌아가 고쳐야 한다고 안내하고 다음 단계 진행 질문(1-5) 대신 재작업 여부를 묻는다. |

커밋하기로 했으면(1·2단계) **이 오케스트레이터가 직접(서브에이전트가 아니라) 실행한다** —
이전 스킬들과 동일한 커밋 관례를 따른다:

- `git status`로 이 단계와 무관한 변경이 섞여 있지 않은지 확인하고, 관련 파일만 스테이징한다
  (`git add -A` 금지).
- 커밋 메시지는 저장소 관례(`git log` 최근 커밋 참고, `type: 한글 설명` 형태)를 따르고, 본문에는
  무엇을 바꿨는지가 아니라 왜 바꿨는지를 적는다. `Co-Authored-By: Claude Sonnet 5
  <noreply@anthropic.com>` 트레일러를 포함한다.
- 원격에 push하지 않는다.

### 1-5. 다음 단계 진행 여부 확인

AskUserQuestion으로 "다음 단계(`<n+1>단계 이름>`)로 진행할까요?"를 묻는다. 4단계(판정)까지
끝난 뒤에는 대신 "이 티켓을 마칠까요, 아니면 확인할 게 더 있나요?"를 묻는다. "아니오"를 고르면
여기서 멈추고, 지금까지 진행 상황(어느 단계까지 끝났고 무엇이 커밋됐는지)을 요약해 보고한 뒤
스킬을 종료한다.

## 2. 전체 종료

4단계(판정)까지 통과하고 커밋됐다면 티켓이 끝난 것이다. 이 세션에서 생긴 커밋 해시를 단계
순서대로 나열해 최종 보고한다.
