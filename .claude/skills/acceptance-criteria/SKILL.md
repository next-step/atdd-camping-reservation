# 인수 조건 작성

`docs/plan.md`의 1단계("인수 조건")를 처리한다. 이 스킬은 **1단계까지만** 담당한다.
인수 테스트 작성(2단계)이나 구현(3단계)에는 관여하지 않는다 — 코드나 테스트 파일을 건드리지 않는다.

이 스킬을 시작하기 전에 `docs/principles.md`와 `docs/plan.md`를 아직 읽지 않았다면 먼저 읽는다
(`CLAUDE.md`에 명시된 규칙).

## 사용 예시

```
/acceptance-criteria T-4
```

동작 흐름: `docs/tickets.md`의 `T-4`("예약 수정 시 체류 기간 30일 제한이 적용되지 않음")를 읽고, 요구사항이
"체류 기간(startDate~endDate)이 30일을 초과하면 거부한다" 하나로 명확하므로 추가 질문 없이 진행한다.
서버를 띄워 생성(POST) 경로가 이미 정상임을 확인하고, 수정(PUT) 경로에서 ①`startDate`+`endDate`를
함께 31일로 바꾸는 경우, ②`endDate`만 단독으로 바꿔 31일을 초과시키는 경우 모두 검증 없이
200으로 성공하는 버그를 실측한 뒤 `docs/acceptance-criteria.md`에 `# T-4 인수 조건` 블록으로 남긴다.

## 0. 입력 확인

인자로 티켓 ID(`T-n`)를 받는다.

- 인자가 없으면 `docs/tickets.md`를 읽어 아직 `docs/acceptance-criteria.md`에 `# T-n 인수 조건`
  블록이 없는 티켓 목록을 보여주고, 어떤 티켓을 다룰지 AskUserQuestion으로 묻는다.
- 티켓 본문이 자유 서술형이라 "이 티켓에서 다룰 요구사항"이 한 문장으로 명확히 안 떨어지는 경우
  (예: T-4, T-5처럼 코드 결함을 서술만 하고 요구사항 문장이 없는 경우), 착수 전에
  AskUserQuestion으로 이번에 다룰 요구사항 범위를 확정한다. 인자로 요구사항 설명이 이미 주어졌으면
  그것을 그대로 범위로 삼되, 애매하면 확인 질문을 한다.

## 1. 컨텍스트 로드

다음을 읽는다:

- `docs/principles.md`, `docs/plan.md`
- `docs/acceptance-criteria.md`, `docs/tickets.md`

`docs/acceptance-criteria.md`에서 가장 마지막 `# T-n 인수 조건` 블록과 `docs/tickets.md`에서
가장 큰 `T-n` 번호를 확인해, 새 티켓을 만들어야 할 때 다음 번호를 알아 둔다 (번호가 연속일
필요는 없다 — 이 저장소는 T-3이 결번이다).

## 2. 코드에서 현재 동작 파악

- 티켓이 언급한 기능과 관련된 코드를 `src/main/java/com/camping/legacy`에서 찾는다.
- `CLAUDE.md`가 지목한 알려진 중복 지점(날짜 정책이 생성/수정 양쪽에 각각 하드코딩, 가격/포인트
  계산 로직이 정식 경로와 인라인 경로로 중복)에 해당하는 티켓이면, 반드시 생성(POST)과 수정(PUT) 등
-  모든 경로 코드를 확인한다. 한쪽만 보고 결론 내지 않는다.
- 관련 검증이 어떤 순서로 실행되는지(무엇을 먼저 체크하는지) 메모해 둔다 — 3단계(구현)에서
  이 순서를 지켜야 하므로, 여기서 파악한 것을 `이유`에 남긴다.

## 3. 실제 서버 기동

- `lsof -i :8080`으로 8080이 이미 떠 있는지 확인한다.
- 비어 있으면 `./gradlew bootRun`을 백그라운드로 실행한다. 충돌하면
  `SERVER_PORT=8081 ./gradlew bootRun`으로 띄운다.
- `/api/sites` 등에 curl로 폴링해 기동 완료를 확인한 뒤에만 다음 단계로 넘어간다.
- `application.yml`이 `ddl-auto: create-drop` + `defer-datasource-initialization`으로
  `data.sql`을 매 기동마다 재적용한다는 점을 유념한다. 예시를 설계하기 전에 `data.sql`을 읽어
  시드 예약(현재 5건: A-1, A-2, A-3, A-4, A-6)과 실존 사이트 번호(A-1~A-20, B-1~B-15)를
  확인하고, 성공 예시에는 시드가 쓰지 않는 사이트를 쓴다.

## 4. 경계 예시 설계 및 실측 — 응답을 지어내지 않는다

이번 단계의 핵심 원칙(`docs/principles.md` "실측에 근거한 판정"): **코드를 읽고 응답을 추정해서
쓰지 않는다. 모든 예시는 실제로 `curl`을 호출해 받은 응답을 그대로 옮긴다.**

요구사항마다 최소 아래 경계를 설계해 실측한다 (`T-1 요구사항 1` 패턴 참고):

1. 허용되는 경계값 (예: "30일 이내"라면 정확히 30일째)
2. 그 경계를 첫 번째로 벗어나는 값 (31일째)
3. 명백히 벗어난 값 (경계와 멀리 떨어진 값 — 회귀 시 더 쉽게 드러남)

생성/수정 둘 다 적용되는 규칙이면 두 경로 모두 실측한다. 수정 경로는 "관련 필드 일부만 보낸
경우"를 반드시 별도로 실측한다 — 이 저장소에서는 부분 업데이트가 검증을 우회하는 버그를 여러 번
숨겼다 (T-1의 "startDate만 수정", T-2의 "phoneNumber 필드 생략 시 기존값 유지").

각 실측 결과를 분류한다:

| 라벨 | 의미 |
| --- | --- |
| `(현재 버그)` | 요구사항과 다르게 동작한다 — 3단계에서 고쳐야 할 대상 |
| `(현재 정상)` | 이미 요구사항대로 동작한다 |
| `(현재 정상, 회귀 방지)` | 이미 정상이지만 이번에 처음 인수 조건으로 명시 — 앞으로 안 깨지게 고정 |
| `(참고용)` | 관련은 있으나 이 요구사항의 정식 조건은 아님 — 별도 티켓 후보 (6단계 참고) |

## 5. `docs/acceptance-criteria.md`에 작성

파일 끝에 아래 형식을 그대로 이어 붙인다. 신규 티켓이면 `# T-n 인수 조건`부터 시작하고, 기존
티켓에 요구사항을 추가하는 것이면 해당 티켓의 `## 요구사항` 번호 목록에 항목을 추가한 뒤 그 아래
이어지는 마지막 `---` 다음 자리에 새 `## 요구사항 n: ...` 블록을 붙인다.

~~~markdown
## 요구사항 N: <요구사항 한 줄 서술>

<POST/PUT 적용 범위와 트리거 조건을 1~3문장으로. "생성(POST)과 수정(PUT) 모두 적용하며..." 형태로
적용 범위를 명시한다.>

## 예시

기준일: <오늘 날짜 YYYY-MM-DD>

### 허용 — <짧은 라벨> (<라벨 태그>)

```
<METHOD> /api/<path>
{ ...요청 바디... }
```

실측 응답:
```json
{ ...curl로 받은 실제 응답 그대로... }
```
→ HTTP <코드>. <한 줄 해석>

### 거부 — <짧은 라벨> (<라벨 태그>)

... (허용/거부 블록을 실측한 개수만큼 반복. 버그인 경우 "실측 응답:" 대신
"실측 응답 (현재 동작 — 버그):"로 쓴다)

## 이유

<원인이 된 신고/티켓 인용, 관련 코드 file:line 인용, 왜 지금이 틀렸는지 또는 왜 회귀 방지가
필요한지를 설명한다.>

---
~~~

새 티켓이면 이 블록 전체를 `# T-n 인수 조건` 헤더와 `## 요구사항` 번호 목록(전체 요구사항을
번호로 나열) 뒤에 붙인다 — `docs/acceptance-criteria.md`의 기존 `# T-1 인수 조건`,
`# T-2 인수 조건` 블록 구조를 그대로 따른다.

## 6. 판단이 필요한 지점 처리

- **이 티켓 범위 안에서** 결정해야 하는데 요구사항이 애매하면, 그 자리에서 AskUserQuestion으로
  묻는다 (`docs/plan.md` 1단계 AI 지시 — "판단이 필요한 부분은 질문한다").
- **이 티켓 범위 밖**에서 발견됐거나 요구사항 자체가 침묵하는 정책(예: 유일성 제약처럼 누구도
  정한 적 없는 규칙)은 스스로 판단하지 않고 `docs/tickets.md`에 새 티켓으로 남긴다.
  `T-6`, `T-7` 패턴을 그대로 따른다:

```markdown
T-<n> <제목>

내용: T-<원본 티켓> 작업 중 확인. <발견 경위와 관련 코드 file:line 인용>
<무엇이 애매한지>는 요구사항이 침묵하므로 이 티켓에서는 판단하지 않는다.

---
```

- 4단계에서 `(참고용)`으로 분류한 예시가 있고 아직 정식 조건으로 다뤄진 적 없다면, 그 자체를
  후속 티켓으로 남길지 검토한다 (T-7이 이 패턴으로 생겼다).

## 7. 마무리 전 확인

- `docs/acceptance-criteria.md`에 적은 모든 "실측 응답"이 이번 세션에서 실제로 curl한 결과인지
  다시 확인한다. 재사용하거나 추정한 값이 하나라도 있으면 다시 호출해 바꾼다.
- `docs/tickets.md`에 새 티켓을 추가했다면 번호가 겹치지 않는지, `---`로 다른 항목과 구분됐는지
  확인한다.
- 코드나 테스트 파일은 건드리지 않았는지 확인한다 — 이 스킬은 2단계(인수 테스트) 이전에서 멈춘다.
- 작업 요약을 짧게 보고한다: 어떤 요구사항을 몇 개의 예시로 실측했는지, 새로 생긴 티켓이 있는지,
  아직 열려 있는 질문이 있는지.
