# 3단계 — 구현

실패하는 인수 테스트를 통과시키는 **최소 변경**을 만든다.

## 읽는 것

| 파일 | 왜 |
|---|---|
| 실패하는 인수 테스트 | 무엇을 통과로 볼지는 여기만 정한다 |
| `docs/acceptance-criteria.md` | 메시지 전문과 상태 코드 |
| `docs/code-guide.md` | 코드가 지켜야 하는 제약 |
| 손댈 클래스의 호출부 | 새 메서드를 어디 둘지 판정할 근거 |

## 하는 일

### 1. 테스트가 시키는 것만 만든다

인수 조건에 없는 규칙을 함께 넣지 않는다. 
1단계에서 티켓으로 넘긴 것(침묵하는 자리)은 **여기서도 처리하지 않는다.**

상태 코드와 메시지는 인수 조건에 적힌 전문 그대로 쓴다. 
경로마다 지금 형태가 다르면 통일하지 않고 각 경로를 따른다.

`docs/code-guide.md` 의 규칙을 지킨다. 지킨 자리를 코드의 어디인지로 짚어 보인다.

### 2. 통과를 확인한다

```bash
./gradlew test --tests '*ReservationAcceptanceTest*'
./gradlew test --rerun-tasks          # 결과 줄이 안 보이면 캐시다
```

## 남기는 것

- 프로덕션 코드
- 커밋 `feat: T-N ... 적용`

인수 조건이나 테스트를 고쳐서 통과시키지 않는다. 테스트가 틀렸다고 판단되면 고치지 말고 **2단계로 돌려보낸다.**

## 자기 점검

- [ ] 실패하던 인수 테스트가 **전부** 통과하는가
- [ ] 인수 조건에 없는 규칙을 함께 넣지 않았는가
- [ ] `code-guide.md` 규칙을 하나씩 짚어 지켰는지 확인했는가

## 다음에 할 것

`/atdd-4-verify` — 티켓이 끝났는지 판정한다.

**여기서 멈춘다.** 테스트가 초록인 것과 티켓이 끝난 것은 다르다.

## 넘어가기 전에 사람이 확인할 것

- 최소 변경인가. 이번 티켓 밖의 동작을 함께 바꾸지 않았는가
- 검증이 놓인 자리가 맞는가. 생성 경로에만 걸렸다면 그것이 의도한 범위인가
- 통과시키려고 인수 조건이나 테스트를 손대지 않았는가
