# 2단계 — 인수 테스트

인수 조건을 실행 가능한 판정으로 옮긴다. **프로덕션 코드는 만지지 않는다.**

## 읽는 것

| 파일 | 왜 |
|---|---|
| `docs/acceptance-criteria.md` | 이번 티켓 절. 시나리오 하나가 테스트 하나 |
| `docs/test-guide.md` | 초안이 지켜야 하는 제약 |
| `src/test/.../acceptance/` | 기존 공통 호출부와 바탕 클래스 |
| `src/main/resources/data.sql` | 시드가 점유한 사이트 |

## 하는 일

### 1. 초안을 내기 전에 먼저 밝힌다

세 줄로 밝히고 시작한다. 코드보다 이것이 먼저다.

- **무엇을 단언했는가** — 상태 코드, 메시지 전문, 그리고 거절 뒤 상태
- **무엇으로 실행했는가** — 실제 서버, HTTP 호출
- **어떻게 격리했는가** — 어느 사이트를 썼고 왜 그 사이트인가

### 2. 제약을 지켜 쓴다

`docs/test-guide.md` 의 규칙을 전부 지킨다. 
초안을 내면서 **각 규칙을 어떻게 지켰는지 규칙 제목으로 짚어 보인다.**
지키지 못한 규칙이 있으면 이유를 밝힌다.

### 3. 실행해서 실패를 확인한다

```bash
./gradlew test --tests '*ReservationAcceptanceTest*'
./gradlew test --rerun-tasks          # 결과 줄이 안 보이면 캐시다
```

**실행만 하고 고치지 않는다.** 실패 메시지를 그대로 보이고, 그 실패가 신고된 증상과 **같은 이유**인지 확인해 보인다.
컴파일 오류나 사이트 겹침으로 실패한 것은 증상 재현이 아니다.

## 남기는 것

- 테스트 코드 — 인수 조건의 시나리오 하나당 테스트 하나
- 커밋 `test: T-N ... 인수 테스트 추가`

**`docs/test-guide.md` 는 쓰지 않는다.** 초안에 새로 건 제약이 있으면 "여기가 규칙이 될 자리"라고 짚고 넘긴다. 규칙으로 굳힐지는 사람이 정한다.

## 자기 점검

- [ ] 새로 쓴 테스트가 **지금 실패**하는가. 실패하지 않으면 지금 동작을 겨눈 초안이다 — 다시 쓴다
- [ ] 실패 이유가 신고된 증상과 같은가. 겹침·컴파일로 실패한 것이 아닌가
- [ ] 회귀 규칙도 테스트로 옮겼는가. 그것은 **지금 통과**해야 한다
- [ ] 거절 케이스에서 상태 코드만 보고 끝내지 않았는가

## 다음에 할 것

`/atdd-3-implement` — 실패하는 테스트를 통과시킨다.

**여기서 멈춘다.** 실패를 보고 그 자리에서 구현으로 넘어가지 않는다.

## 넘어가기 전에 사람이 확인할 것

- 테스트가 인수 조건의 규칙을 검증하는가, 아니면 통과하기 쉬운 것을 검증하는가
- 실패 메시지가 신고된 증상과 같은 이유인가
- 짚어 온 "규칙이 될 자리"를 `docs/test-guide.md` 에 한 줄로 굳힐 것인가
