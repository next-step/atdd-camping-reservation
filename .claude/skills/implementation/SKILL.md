이 스킬은 `docs/plan.md`의 "3. 구현" 단계를 실행한다. 절차의 권위 있는 출처는 언제나
`docs/plan.md`와 `docs/principles.md`다 — 이 저장소마다 고쳐 쓰는 뼈대 문서이므로, 아래
요약이 아니라 **매번 그 두 파일을 다시 읽고** 따른다. 이 SKILL.md는 그 절차를 이
저장소의 실제 파일·컨벤션에 맞게 구체화한 것뿐이다.

경로는 모두 저장소 루트(`atdd-camping-reservation/`) 기준이다. 별도의 드라이버를 새로
만들지 않는다 — `acceptance-test` 스킬이 이미 만든
`.claude/skills/acceptance-test/run-tests.sh`를 그대로 재사용한다(테스트를 돌려 실패를
확인하는 방법은 2단계와 3단계가 같다).

## 입력

기본값: 지금 실패하는 인수 테스트 전부. 사용자가 티켓 번호나 특정 테스트 클래스/메서드를
짚어주면 그 범위만 다룬다.

## 절차

1. **뼈대 문서 재확인** — `docs/plan.md`의 "3. 구현" 절과 `docs/principles.md` 전체를
   읽는다. 특히 "기준을 세운 뒤 코드 수정"과 "만드는 쪽과 판정하는 쪽의 분리" 원칙을
   이번 실행에 적용한다.
2. **실패 확인** — `.claude/skills/acceptance-test/run-tests.sh`(범위가 정해졌으면
   `--tests` 패턴 포함)로 지금 실패하는 테스트를 찾는다. `build/test-results/test/*.xml`
   또는 콘솔 출력에서 실패 메시지(기대값 vs 실제값)를 정확히 읽는다 — 짐작하지 않는다.
3. **원인 추적** — 실패한 테스트가 호출하는 API 경로를 따라 Controller → Service →
   도메인까지 내려가서 기대값과 어긋나는 지점을 정확히 짚는다. 같은 티켓을 다루며
   `acceptance-criteria`/`acceptance-test` 스킬이나 이전 대화에서 이미 원인을 분석해
   뒀으면 그 결과를 재사용하고 처음부터 다시 분석하지 않는다.
4. **최소 수정** — 그 테스트(들)를 통과시키는 데 필요한 최소한의 변경만 한다. 같은
   원인으로 여러 테스트가 실패하면 한 번에 고치되, 관련 없는 리팩터링·정리·다른
   실패와 무관한 코드는 건드리지 않는다(`principles.md`와 `CLAUDE.md`의 공통 지침).
   **테스트 코드는 건드리지 않는다** — 그건 `acceptance-test` 스킬의 산출물이다. 테스트
   자체가 잘못됐다고 판단되면 고치지 말고 질문으로 남긴다(아래 "하지 않는 것" 참고).
5. **재실행해서 통과 확인** — 고친 부분과 관련된 테스트를 `run-tests.sh --tests ...`로
   다시 돌려 통과하는지 확인한다. 바로 인접한 테스트(같은 클래스 등)도 같이 돌려 즉시
   깨진 게 없는지 가볍게 확인한다 — 전체 스위트 회귀 확인은 4단계(판정)의 몫이라 여기서
   다시 하지 않는다.
6. **요약 보고** — 사용자에게 반드시 아래 형식으로 알려준다:
   - **어디**: 파일 경로:줄 번호
   - **어떻게**: 무엇을 바꿨는지(가능하면 변경 전/후 코드 스니펫)
   - **왜**: 어떤 규칙·테스트·티켓을 만족시키기 위함인지

## 출력

- 수정된 프로덕션 코드(커밋 안 함)
- `run-tests.sh` 재실행 결과: 방금 전엔 실패했는데 지금은 통과하는지
- 위 형식의 변경 요약(어디/어떻게/왜)

## 하지 않는 것

- 테스트 코드는 수정하지 않는다 — 테스트가 틀렸다고 판단되면 고치지 않고 사용자에게
  질문으로 남긴다.
- 관련 없는 리팩터링·정리를 하지 않는다 — 실패하는 테스트를 통과시키는 데 필요한
  변경만 한다.
- 전체 회귀 스위트를 돌리지 않는다 — 4단계(판정)의 몫이다.
- 커밋하지 않는다(사용자가 말할 때만).

## Gotchas

- `run-tests.sh`는 `test` 태스크에 `JAVA_TOOL_OPTIONS`로 인코딩을 강제하지 않는다 —
  `acceptance-test` 스킬의 Gotchas에 이미 이유가 적혀 있다(강제하면 Gradle 테스트 워커
  IPC가 깨져 `ClassNotFoundException`이 남).
- `./gradlew test`는 소스가 안 바뀌면 `UP-TO-DATE`로 캐시돼서 통과/실패 줄이 안 보일 수
  있다 — `run-tests.sh`는 항상 `--rerun-tasks`를 붙이니 이 스킬 안에서는 문제 없지만,
  스킬 밖에서 직접 `./gradlew test`만 돌려서 "고쳤는데 그대로 실패"라고 오판하지 않는다.
