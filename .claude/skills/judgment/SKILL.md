이 스킬은 `docs/plan.md`의 "4. 판정" 단계를 실행한다. 절차의 권위 있는 출처는 언제나
`docs/plan.md`와 `docs/principles.md`다 — 이 저장소마다 고쳐 쓰는 뼈대 문서이므로, 아래
요약이 아니라 **매번 그 두 파일을 다시 읽고** 따른다. 이 SKILL.md는 그 절차를 이
저장소의 실제 파일·컨벤션에 맞게 구체화한 것뿐이다.

경로는 모두 저장소 루트(`atdd-camping-reservation/`) 기준이다. 새 드라이버를 만들지
않는다 — 앞 단계 스킬 둘이 만든 것을 그대로 재사용(조합)한다:
- `.claude/skills/acceptance-test/run-tests.sh` — 전체 테스트로 회귀 확인
- `.claude/skills/acceptance-criteria/verify-api.sh` — 서버를 UTF-8로 띄워 기존 API를
  직접 호출로 확인

## 입력

바뀐 코드와 지금까지 쌓인 테스트 전부 (`git diff`로 현재 작업트리의 변경, 그리고
`src/test/java/com/camping/legacy/acceptance/`의 전체 테스트).

## 절차

1. **뼈대 문서 재확인** — `docs/plan.md`의 "4. 판정" 절과 `docs/principles.md` 전체를
   읽는다.
2. **바뀐 코드 요약** — `git status`/`git diff`로 지금 작업트리의 변경을 모두 살펴보고,
   무엇을·어디를·왜 바꿨는지 사용자에게 설명한다(구현 스킬이 이미 준 요약이 있으면
   재사용하되, 실제 diff와 다시 대조해서 빠진 게 없는지 확인한다).
3. **전체 테스트로 회귀 확인** — `.claude/skills/acceptance-test/run-tests.sh`를
   **인자 없이**(전체 스위트) 돌린다. 몇 개 중 몇 개 통과/실패했는지, 실패했다면 어떤
   테스트인지 정리한다.
4. **기존 API 직접 확인** — `.claude/skills/acceptance-criteria/verify-api.sh start`로
   서버를 UTF-8 인코딩으로 띄우고, 이번 변경과 직접 관련 없는 기존 엔드포인트 몇
   개(예: 시드 데이터 조회, 이전에 고쳤던 케이스의 반대편 케이스)를 실제로 호출해서
   여전히 정상 동작하는지 확인한다. `docs/plan.md`가 명시한 인코딩 문제(JDK17 + 한글
   Windows에서 `-Dfile.encoding=UTF-8` 없이 띄우면 `data.sql` 한글이 깨짐)를 여기서
   챙긴다 — `verify-api.sh`가 이미 처리한다. 확인이 끝나면 `verify-api.sh stop`으로
   반드시 정리한다.
5. **판정 보고** — 사용자에게 정리해서 알려준다:
   - 요구사항대로 됐는지(관련 인수 테스트 통과 여부)
   - 원래 되던 것이 안 깨졌는지(전체 회귀 결과 + 직접 호출로 확인한 기존 API 결과)
   - 확인 절차를 어떻게 수행했는지(무엇을 돌렸고 무엇을 호출했는지)
6. **발견한 것은 티켓으로** — 판정 과정에서 새로 발견한 문제가 있으면
   `docs/tickets.md`에 기존 형식대로 추가하고 사용자에게 알린다.
7. **승인 후 커밋** — 사용자가 승인하기 전에는 커밋하지 않는다. 승인되면 이번 티켓
   작업과 관련된 변경만 커밋한다 — **이 세션에서 이미 별도로 커밋된 스킬 파일
   (`.claude/skills/**`)은 다시 포함하지 않는다.** 커밋 전 `git status`로 무엇이
   올라가는지 사용자에게 다시 한번 보여준다.

## 출력

- 바뀐 코드 요약(파일:줄, 무엇을, 왜)
- 전체 테스트 실행 결과
- 기존 API 직접 호출 확인 결과
- (있다면) 새로 남긴 티켓
- 사용자 승인 후: 커밋

## 하지 않는 것

- 사용자가 승인하기 전에는 커밋하지 않는다.
- `.claude/skills/**`(스킬 자체 파일)는 이 스킬의 커밋 대상이 아니다 — 그건 각 단계
  스킬을 만들 때 별도로 커밋한다.
- 실패하는 테스트를 다시 고치지 않는다 — 그건 3단계(구현)의 몫이다. 여기서는 판정만
  한다(원인 분석까지는 하되, 코드 수정은 사용자 확인 후 별도로).

## Gotchas

- `verify-api.sh`로 서버를 띄운 뒤에는 반드시 `stop`으로 정리한다 — 안 그러면 다음
  실행(예: `run-tests.sh`가 같은 포트를 쓰는 건 아니지만, 8081에 떠 있는 서버가 계속
  남는다) 때 헷갈린다.
- `run-tests.sh`와 `verify-api.sh`는 서로 다른 이유로 인코딩을 다르게 다룬다 —
  `verify-api.sh`(bootRun 계열)는 `JAVA_TOOL_OPTIONS`로 UTF-8을 강제해야 하고,
  `run-tests.sh`(test 태스크)는 그러면 안 된다(Gradle 테스트 워커 IPC가 깨짐). 각
  스킬의 Gotchas에 이미 적혀 있다 — 섞어 쓰지 않는다.
